Chapter 2 — Tokens, Tokenization & Context Windows

Quick Take

Human language is messy — prefixes, suffixes, punctuation, emoji, code, and multilingual text don't fit a one-word-one-token model. Tokenizers optimize for statistical efficiency, not human readability. The gap between word count and token count can surprise you.

Deep Dive

Tokenizers use learned merge rules to find the most compact representation of training data. Common words like "the" or "and" earn dedicated single tokens because they appear millions of times. Rare or morphologically complex words get split: "unhappiness" becomes ["un","happ","iness"] or similar. This is a feature, not a bug — it lets the model handle any string, even ones it has never seen, by decomposing them into familiar pieces.

Structured data like JSON, XML, and source code are especially token-hungry. Every bracket, colon, quotation mark, and whitespace character can consume a separate token. A compact-looking JSON blob might use 2 to 3 times more tokens than an English sentence of similar visual length. Multilingual text without spaces — Chinese, Japanese, Thai — often fragments into many small byte-level pieces, each burning a token.

The practical upshot: a "short-looking" prompt can be expensive, and a "long-looking" one cheap. When you care about cost, latency, or fitting within a context window, always measure in tokens, never in words or characters.

Code

import tiktoken

enc = tiktoken.encoding_for_model("gpt-4")

examples = [
    "The cat sat on the mat.",
    '{"name": "Alice", "age": 30}',
    "日本語のテキスト処理",
    "unhappiness, antidisestablishmentarianism"
]
for text in examples:
    tokens = enc.encode(text)
    words  = text.split()
    print(f"Words: {len(words):2d} | Tokens: {len(tokens):2d} | {text}")
