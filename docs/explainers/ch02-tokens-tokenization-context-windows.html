How LLMs convert raw text into computable units — and why every engineering decision downstream traces back to the token.

What Is a Token?

A token is the atomic unit an LLM processes — not a word, not a character, but a statistical building block learned from training data. Every cost, speed, and memory metric is measured in tokens.
💡 A token is to an LLM what a pixel is to an image — the smallest unit the system can see.

From Text to Numbers

LLMs cannot read text. They operate on sequences of integers drawn from a fixed vocabulary — typically 32,000 to 200,000 entries. A tokenizer converts raw text into these integers and back again.

Each vocabulary entry maps a string fragment (a "token") to an integer ID. The fragment might be a whole word like "the", a subword like "tion", a single character, or even a partial byte sequence. The mapping is learned during training and frozen afterward.

Token Economy

Every interaction with an LLM is billed in tokens. When you see pricing like "$3 per million input tokens," that's referring to these atomic units — not words, not characters. Understanding this distinction is critical for cost modeling.

  • Input tokens — your prompt, system message, and any context you provide
  • Output tokens — the model's response, generated one token at a time
  • Cached tokens — previously seen prefixes that some APIs discount

A single English word averages roughly 1.3 tokens. Code tends toward 1.5–2x. Non-Latin scripts can hit 3–4x. These ratios directly impact what you pay and how much context you can fit. See Topic 2: Tokens vs Words for detailed fertility analysis.

Why This Matters in Practice

Every constraint you encounter — rate limits, context window size, latency targets, monthly budgets — is denominated in tokens. If you're optimizing prompts, estimating costs, or debugging truncation issues, you need to think in tokens, not words.

Speed is also token-bound: models generate output at a fixed rate of tokens per second, not words per second. A 100-token response of dense code might contain far fewer "words" than a 100-token response of simple English, but both take the same time to generate. For how token counts affect your bill, see Topic 7: Understanding Costs.

→ Tokens are the atomic currency of LLMs — if you don't understand tokenization, you can't reason about cost, speed, or capacity.
Python Example
import tiktoken

# Load the tokenizer used by GPT-4 / GPT-4o
# "o200k_base" is the encoding name; each model family has its own
enc = tiktoken.get_encoding("o200k_base")

text = "Tokenization is surprisingly nuanced!"

# encode() converts a string → list of integer token IDs
token_ids = enc.encode(text)
print(f"Token IDs : {token_ids}")
# → [3404, 2065, 382, 25675, 88898, 0]

# decode() converts token IDs back → string
decoded = enc.decode(token_ids)
print(f"Round-trip : {decoded}")
# → "Tokenization is surprisingly nuanced!"

# decode_single_token_bytes() shows the raw bytes for one token
# This reveals what each ID actually represents
for tid in token_ids:
    token_bytes = enc.decode_single_token_bytes(tid)
    print(f"  ID {tid:>6d} → {token_bytes}")
# → ID   3404 → b'Token'
# → ID   2065 → b'ization'
# → ID    382 → b' is'
# → ID  25675 → b' surprisingly'
# → ID  88898 → b' nuanced'
# → ID      0 → b'!'

# Key insight: "Tokenization" splits into "Token" + "ization"
# because the full word isn't in the vocabulary, but both
# subwords are — this is BPE in action (see Topic 3)
print(f"\nCharacters : {len(text)}")
print(f"Tokens     : {len(token_ids)}")
print(f"Ratio      : {len(text)/len(token_ids):.1f} chars/token")
Follow-up Questions
How does vocabulary size affect model performance?
Larger vocabularies (100K–200K) produce fewer tokens per input, improving speed and fitting more text in the context window. The tradeoff is a larger embedding matrix, which increases model size and memory usage. Most modern models settle around 100K–200K as the sweet spot.
Why do different models tokenize the same text differently?
Each model family trains its own tokenizer on its own training corpus. GPT-4 uses o200k_base, Claude uses its own BPE variant, and Llama uses SentencePiece. Different training data produces different merge rules and different vocabularies.
What happens when a model encounters text it has never seen?
Modern tokenizers using byte-level BPE can always fall back to individual bytes, so nothing is truly "unseen." The text just gets split into more, smaller tokens — which costs more and may reduce comprehension quality.
How does the tokenizer handle whitespace and newlines?
Most modern tokenizers encode leading whitespace as part of the token itself — " the" (with a space) is a different token than "the". Newlines, tabs, and multiple spaces each get their own tokens or are absorbed into adjacent tokens. This is why formatting changes can alter token counts.

Tokens vs Words

Human language is messy — prefixes, suffixes, code, emoji, and multilingual text break any clean word-to-token mapping. Tokenizers optimize for statistical efficiency, not readability.
💡 If words are whole LEGO bricks, tokens are the studs and plates — the model builds meaning from smaller, reusable pieces.

Why the Mismatch Exists

Words are a human concept — we define them by spaces and punctuation. Tokenizers don't care about human conventions. They split text into pieces that minimize the total number of tokens needed to represent the training corpus, which means common substrings get their own tokens regardless of word boundaries.

The word "unbelievable" might tokenize as ["un", "believ", "able"] — three tokens for one word. Meanwhile, "the" is so common it's always a single token. This isn't a flaw; it's a feature. Subword tokenization lets the model reuse pieces like "un-" and "-able" across thousands of words, dramatically improving vocabulary coverage. See Topic 3: Byte-Pair Encoding for how this vocabulary is built.

Fertility: The Hidden Cost Multiplier

Fertility is the average number of tokens per word. English prose has a fertility around 1.3, meaning roughly 4 words per 5 tokens. But this ratio varies wildly:

Input TypeFertilityImpact
Simple English~1.3Baseline — most efficient
Technical English~1.5Jargon and compound terms add tokens
Python / JS code~2.0Syntax, indentation, special chars
JSON / XML~2.5Structural characters dominate
Japanese / Chinese~3.0Each character may be its own token
Emoji sequences~3–8Multi-byte encoding, skin tone modifiers

This means the same semantic content in Japanese can cost 2–3x more in API fees than English, simply due to tokenization. For cost implications, see Topic 7: Understanding Costs.

→ The token-to-word ratio (fertility) is what really determines your API cost — and it varies 10x across input types and languages.
Python Example
import tiktoken

enc = tiktoken.get_encoding("o200k_base")

# Compare fertility (tokens per word) across different input types
samples = {
    "English prose": "The quick brown fox jumps over the lazy dog near the river bank.",
    "Technical text": "The transformer architecture uses multi-head self-attention mechanisms.",
    "Python code":   "def fibonacci(n): return n if n <= 1 else fibonacci(n-1) + fibonacci(n-2)",
    "JSON data":     '{"user": {"name": "Alice", "scores": [98, 87, 95], "active": true}}',
    "Japanese":      "今日は天気がいいですね。散歩に行きましょう。",
}

print(f"{'Input Type':<20} {'Words':>6} {'Tokens':>7} {'Fertility':>10}")
print("-" * 48)

for label, text in samples.items():
    # Count words the human way (split on whitespace)
    word_count = len(text.split())

    # Count tokens the model way
    token_ids = enc.encode(text)
    token_count = len(token_ids)

    # Fertility = tokens per word
    # Higher fertility → more expensive per "word" of meaning
    fertility = token_count / max(word_count, 1)

    print(f"{label:<20} {word_count:>6} {token_count:>7} {fertility:>9.2f}x")

# Output shows that code and non-Latin text cost significantly
# more tokens per word of semantic content — this directly
# impacts your API bill and context window usage
Follow-up Questions
Does it really cost more to use non-English languages with LLMs?
Yes, measurably. A Japanese or Arabic prompt may use 2–3x as many tokens as English for the same meaning, directly increasing cost. Newer tokenizers like o200k_base have improved multilingual efficiency, but a gap remains.
Can I write prompts to be more token-efficient?
Somewhat. Removing redundant whitespace, using common words over rare jargon, and preferring concise phrasing all help. But the gains are modest — 10–20% at best. The biggest lever is choosing what to include, not how to phrase it.
Should I chunk text by tokens or by words when building RAG systems?
Always chunk by tokens. Word-based chunking leads to unpredictable token counts, which can cause context window overflows. Use tiktoken (or your model's tokenizer) to count and split precisely.

Byte-Pair Encoding (BPE)

BPE builds a vocabulary bottom-up — start with characters, repeatedly merge the most frequent pair. Common patterns get compact tokens; rare words decompose gracefully.
💡 BPE is like learning shorthand — the most common letter pairs get abbreviations first, then common abbreviations get combined into longer ones.

The UNK Problem BPE Solved

Early NLP systems used fixed word-level vocabularies. Any word not in the vocabulary became <UNK> — a single "unknown" token that destroyed meaning. Misspellings, neologisms, technical jargon, and foreign words all collapsed into the same meaningless placeholder.

BPE, adapted from a 1994 data compression algorithm by Sennrich et al. (2016), solved this by operating at the subword level. No input is ever truly unknown — it just decomposes into smaller, known pieces.

The Algorithm Step by Step

  1. Initialize: Split every word in the training corpus into individual characters. Each character is a token.
  2. Count pairs: Find the most frequently adjacent pair of tokens across the corpus.
  3. Merge: Replace every occurrence of that pair with a new single token. Add the new token to the vocabulary.
  4. Repeat: Go to step 2. Continue until you reach the desired vocabulary size (e.g., 50,000 merges).

The order of merges is saved as the "merge table" and applied at inference time. This is what makes tokenization deterministic — the same text always produces the same tokens.

Vocabulary Size Tradeoffs

Vocab SizeProsCons
Small (8K–16K)Compact model, fast softmaxHigh fertility, poor compression
Medium (32K–50K)Good balance, proven in GPT-2/3Weaker on multilingual text
Large (100K–200K)Better compression, multilingualLarger embedding matrix, memory cost

Which Models Use BPE?

Nearly all major LLMs use BPE or a close variant. GPT-2 through GPT-4 use byte-level BPE (via tiktoken). Claude uses a BPE variant. Llama and Gemma use Topic 4: SentencePiece with BPE mode. The algorithm is so dominant that "tokenizer" and "BPE tokenizer" are often used interchangeably in practice.

→ BPE eliminated the unknown-word problem by ensuring every input can always be decomposed into known subword pieces — no text is unrepresentable.
Python Example
"""
Byte-Pair Encoding from scratch — a minimal but complete implementation.
This mirrors what real tokenizers do, just at a smaller scale.
"""

def get_pair_counts(corpus):
    """Count every adjacent pair of tokens across the corpus.

    Args:
        corpus: list of lists — each inner list is a word split into tokens
    Returns:
        dict mapping (token_a, token_b) → frequency count
    """
    counts = {}
    for word in corpus:
        for i in range(len(word) - 1):
            pair = (word[i], word[i + 1])
            counts[pair] = counts.get(pair, 0) + 1
    return counts


def merge_pair(corpus, pair):
    """Replace every occurrence of `pair` with a single merged token.

    Args:
        corpus: list of lists of tokens
        pair: tuple of two adjacent tokens to merge, e.g. ("t", "h")
    Returns:
        new corpus with the pair merged into one token
    """
    new_corpus = []
    for word in corpus:
        new_word = []
        i = 0
        while i < len(word):
            # If we find the pair, merge it
            if i < len(word) - 1 and (word[i], word[i + 1]) == pair:
                new_word.append(word[i] + word[i + 1])
                i += 2  # skip both tokens
            else:
                new_word.append(word[i])
                i += 1
        new_corpus.append(new_word)
    return new_corpus


# --- Run BPE on a tiny corpus ---

# Start with words split into characters (the initial "vocabulary")
corpus = [
    list("low"),      # → ['l', 'o', 'w']
    list("lower"),    # → ['l', 'o', 'w', 'e', 'r']
    list("newest"),   # → ['n', 'e', 'w', 'e', 's', 't']
    list("widest"),   # → ['w', 'i', 'd', 'e', 's', 't']
    list("lowest"),   # → ['l', 'o', 'w', 'e', 's', 't']
]

num_merges = 8  # In real models this would be 30,000–100,000

print("Initial corpus:")
for w in corpus:
    print(f"  {w}")

merge_rules = []

for step in range(num_merges):
    pairs = get_pair_counts(corpus)
    if not pairs:
        break

    # Find the most frequent pair
    best_pair = max(pairs, key=pairs.get)
    best_count = pairs[best_pair]

    # Merge it everywhere
    corpus = merge_pair(corpus, best_pair)
    merge_rules.append(best_pair)

    print(f"\nStep {step + 1}: merge {best_pair} (count={best_count})")
    for w in corpus:
        print(f"  {w}")

# The merge_rules list IS the tokenizer — apply these merges
# in order to tokenize any new text at inference time
print(f"\nLearned {len(merge_rules)} merge rules:")
for i, rule in enumerate(merge_rules):
    print(f"  {i+1}. {rule[0]} + {rule[1]} → {rule[0]+rule[1]}")
Follow-up Questions
What is byte-level BPE and how does it differ from character-level?
Byte-level BPE starts from the 256 possible byte values instead of Unicode characters. This guarantees any byte sequence can be tokenized — no special handling needed for unusual characters, binary data, or new emoji.
Is there an optimal vocabulary size?
No single optimum exists. Larger vocabularies compress text better (fewer tokens) but increase the embedding matrix size and memory usage. Current best practice lands between 32K and 200K, depending on how multilingual the model needs to be.
How does BPE compare to the Unigram algorithm?
BPE builds vocabulary bottom-up (merging); Unigram works top-down (starting large, pruning). Unigram can assign probabilities to multiple segmentations, enabling sampling-based tokenization. In practice, both produce similar results; BPE is more common in Western-focused models.
Can BPE merges cross word boundaries?
In standard BPE, merges only happen within pre-tokenized words (split by whitespace/punctuation first). Byte-level BPE in GPT-2+ uses regex-based pre-splitting to prevent cross-word merges while still operating on bytes.

Why Whitespace Assumptions Break

Classic tokenizers (like the one in GPT-2) start by splitting text on whitespace and punctuation. This works well for English, where spaces reliably separate words. But many languages don't use spaces between words:

  • Japanese and Chinese — no spaces between words at all
  • Thai and Khmer — spaces separate phrases, not words
  • German — compound words like Geschwindigkeitsbegrenzung are single "words"
  • Agglutinative languages (Turkish, Finnish) — a single word can encode an entire sentence

Requiring language-specific pre-processing for each script doesn't scale. SentencePiece was built to eliminate this dependency entirely.

How SentencePiece Works

SentencePiece, developed by Google (Kudo & Richardson, 2018), treats the input as a raw sequence of Unicode characters — including whitespace. Spaces are replaced with a special ▁ (U+2581) character and treated as just another character to be tokenized.

This means the tokenizer learns where word boundaries are from the data itself, rather than relying on pre-coded rules. The result is a single model file (a .model binary) that handles any language and any script with no external dependencies.

BPE vs Unigram Mode

SentencePiece supports two training algorithms:

FeatureBPE ModeUnigram Mode
DirectionBottom-up (merge)Top-down (prune)
DeterministicYes — one segmentationCan sample alternatives
Used byLlama, Gemma, MistralT5, mBART, ALBERT
StrengthPredictable, well-understoodRegularization via sampling

Both modes produce a single .model file with identical APIs. The choice between them is made at training time and is transparent to downstream users. For the underlying BPE algorithm, see Topic 3: Byte-Pair Encoding.

→ SentencePiece made tokenization truly language-agnostic — one algorithm, one model file, any script.
Python Example
import sentencepiece as spm

# --- Training a SentencePiece model from scratch ---

# Write a small corpus to a file (in practice, use millions of lines)
with open("/tmp/corpus.txt", "w") as f:
    f.write("The quick brown fox jumps over the lazy dog.\n")
    f.write("今日はいい天気ですね。散歩に行きましょう。\n")
    f.write("SentencePiece handles all languages equally.\n")
    f.write("กรุงเทพมหานครเป็นเมืองหลวงของประเทศไทย\n")

# Train the tokenizer — this produces two files:
#   /tmp/sp_demo.model  (the binary model)
#   /tmp/sp_demo.vocab  (human-readable vocabulary)
spm.SentencePieceTrainer.train(
    input="/tmp/corpus.txt",
    model_prefix="/tmp/sp_demo",
    vocab_size=200,             # tiny for demo; real models use 32K–128K
    model_type="bpe",           # or "unigram" for the alternative algorithm
    character_coverage=0.9995,  # ensure rare characters are included
    # Key: no language-specific flags needed — it figures it out
)

# --- Using the trained model ---

sp = spm.SentencePieceProcessor(model_file="/tmp/sp_demo.model")

texts = [
    "The quick brown fox",
    "今日はいい天気ですね",
    "กรุงเทพมหานคร",
]

for text in texts:
    # encode_as_pieces() returns the subword strings
    # Note the ▁ character — it represents a word boundary
    pieces = sp.encode_as_pieces(text)

    # encode_as_ids() returns the integer token IDs
    ids = sp.encode_as_ids(text)

    # decode() reconstructs the original text exactly
    decoded = sp.decode(ids)

    print(f"Text:    {text}")
    print(f"Pieces:  {pieces}")
    print(f"IDs:     {ids}")
    print(f"Decoded: {decoded}")
    print(f"Tokens:  {len(ids)}")
    print()

# Key advantage: same API, same model, any language
# No need for MeCab (Japanese), PyThaiNLP (Thai), etc.
Follow-up Questions
How does SentencePiece compare to tiktoken?
tiktoken is a fast BPE encoder/decoder library (by OpenAI) that applies a pre-trained merge table. SentencePiece is both a trainer and encoder — it can learn new tokenizations from scratch. They solve different parts of the same problem.
What is NFKC normalization and why does SentencePiece use it?
NFKC collapses visually similar characters into a single canonical form — for example, full-width Ａ becomes A. SentencePiece applies this by default to reduce vocabulary waste on duplicate character forms. It can be disabled if exact byte preservation is needed.
Can I add custom pre-tokenization rules to SentencePiece?
Yes. SentencePiece supports custom normalization rules via a TSV file and allows user-defined symbols that are always kept as single tokens. However, adding language-specific splitting rules defeats the purpose — the algorithm works best when it learns segmentation from data.

Special Tokens

Special tokens are invisible structural markers — [BOS], [EOS], [SEP], [PAD] — that tell the model where sequences start, end, and transition. Mishandle them and everything breaks.
💡 Special tokens are like punctuation marks in music notation — rests, bar lines, repeat signs — they don't make sound, but without them the piece falls apart.

Why Fine-Tuning Goes Wrong

The most common fine-tuning bug is incorrect special token handling. If your training data doesn't include the exact special tokens the base model expects, the model learns corrupted turn boundaries. Symptoms include:

  • The model repeats the user's question back as its answer
  • Responses run on indefinitely without stopping
  • The model generates text as if it's the user, not the assistant
  • Multi-turn conversations "forget" earlier messages

The fix is always the same: use the exact chat template the model was trained with. Every <|im_start|>, every newline, every role tag must match exactly. See Topic 1: What Is a Token for how these get encoded into IDs.

Chat Templates and Role Markers

Modern chat models use structured templates to distinguish system instructions, user messages, and assistant responses. The format varies by model family:

ChatML (OpenAI): <|im_start|>system\nYou are helpful.<|im_end|>
Llama format: <s>[INST] <<SYS>>\nSystem prompt\n<</SYS>>\n\nUser message [/INST]
Mistral: [INST] User message [/INST] Assistant response

These templates are not interchangeable. Using Llama's format on a model trained with ChatML produces gibberish. The tokenizer.apply_chat_template() method in HuggingFace Transformers handles this automatically.

→ Special tokens are the skeleton of model input — they're invisible to users but they define every structural boundary the model relies on.
Python Example
from transformers import AutoTokenizer

# Load a chat model's tokenizer — this includes its special tokens
# and chat template definition
tokenizer = AutoTokenizer.from_pretrained("meta-llama/Llama-3.1-8B-Instruct")

# --- Inspect special tokens ---

# Every tokenizer defines these core special tokens
print("Special tokens:")
print(f"  BOS: {tokenizer.bos_token!r}  (ID: {tokenizer.bos_token_id})")
print(f"  EOS: {tokenizer.eos_token!r}  (ID: {tokenizer.eos_token_id})")
print(f"  PAD: {tokenizer.pad_token!r}  (ID: {tokenizer.pad_token_id})")
print(f"  UNK: {tokenizer.unk_token!r}  (ID: {tokenizer.unk_token_id})")

# Additional special tokens vary by model
print(f"\n  All special: {tokenizer.all_special_tokens}")

# --- Build a chat using the model's template ---

messages = [
    {"role": "system", "content": "You are a helpful assistant."},
    {"role": "user", "content": "What is tokenization?"},
    {"role": "assistant", "content": "Tokenization is the process of splitting text into tokens."},
    {"role": "user", "content": "Why does it matter?"},
]

# apply_chat_template() formats messages with the CORRECT special tokens
# for this specific model — no guessing, no manual formatting
formatted = tokenizer.apply_chat_template(
    messages,
    tokenize=False,           # return string, not token IDs
    add_generation_prompt=True  # add the prompt for the next assistant turn
)

print("\n--- Formatted chat template ---")
print(formatted)
# Shows the exact special tokens wrapped around each message

# --- Tokenize and inspect ---

token_ids = tokenizer.encode(formatted)
print(f"\nTotal tokens: {len(token_ids)}")

# Decode each token to see special tokens in context
for i, tid in enumerate(token_ids[:30]):  # first 30 for brevity
    tok_str = tokenizer.decode([tid])
    is_special = tid in tokenizer.all_special_ids
    marker = " ← SPECIAL" if is_special else ""
    print(f"  [{i:3d}] ID {tid:>8d}  {tok_str!r}{marker}")

# Key insight: special tokens have their own reserved IDs
# and are NEVER produced by normal text tokenization —
# they can only appear when explicitly added by the template
Follow-up Questions
How do I debug special token mismatches when fine-tuning?
Decode your training examples token-by-token and check that special tokens appear at the expected positions. Use tokenizer.convert_ids_to_tokens() to inspect. If you see role markers inside regular text or missing turn boundaries, your template is wrong.
What is the ChatML format?
ChatML wraps each message in <|im_start|>role\ncontent<|im_end|>\n tags. It was introduced by OpenAI and is now used by many models. The im stands for "imaginary monologue" — the original internal name for the chat format.
How do special tokens interact with the attention mask?
<PAD> tokens must have an attention mask of 0 so the model ignores them. All other special tokens typically get mask 1 — the model needs to "see" them to understand structure. Incorrectly masking <BOS> or role tokens degrades performance.
System Design

Now that you understand how tokens work, this section covers the engineering constraints they create — context limits, cost, overflow handling, and production budgeting.

Context Window

The context window is the model's working desk — everything it can see at once. System prompt, user input, retrieved docs, and the model's own output all compete for the same fixed space.
💡 The context window is RAM, not a hard drive — only what's loaded can be used, and it's wiped between sessions.

Attention Scope, Not Memory

A context window is not memory in the human sense. The model doesn't "remember" anything from previous requests — each API call starts from a blank slate. What we call "context" is really the full text payload the transformer's attention mechanism (Topic 1) can attend to in a single forward pass.

Think of it as a read-only workspace that gets assembled, processed, and discarded. If a fact isn't in the current window, the model literally cannot use it — no matter how many times you mentioned it in previous conversations.

The Math: 128K Tokens ≈ 96K Words

Context window sizes are measured in tokens, not words. Using the rough 1 token ≈ 0.75 words heuristic for English:

Window≈ Words≈ Pages
4K3,000~6
32K24,000~48
128K96,000~192
200K150,000~300

These are approximations for English prose. Code, JSON, and non-Latin scripts have very different token densities — always count empirically.

Output Eats From the Same Budget

A critical misconception: the context window is shared between input and output. If your window is 128K and you send 127K of input, the model can only generate ~1K tokens of output before hitting the wall.

This means you must reserve space for the model's reply. A typical max_tokens setting of 4,096 means you effectively have 124K for input. Topic 10: Token Budgeting covers how to manage this systematically.

Lost in the Middle

Research shows that even within a context window, models pay uneven attention. Information at the beginning and end of the context is recalled more reliably than information buried in the middle — a phenomenon called "lost in the middle."

  • System prompts at the start get strong attention
  • The most recent user message at the end also gets strong attention
  • Retrieved documents crammed in the middle may be partially ignored

This is why placement matters as much as content, and why more context can actually degrade performance if the new content dilutes the signal.

Longer ≠ Better

Larger context windows are not a universal upgrade. They come with real costs:

  • Latency — attention is O(n²), so doubling context roughly quadruples compute
  • Cost — you pay per token processed, input and output (Topic 7: Cost & Latency)
  • Accuracy — more irrelevant context can confuse the model and degrade answers

The sweet spot is to use just enough context with high relevance content, rather than dumping everything in because you can.

→ Context is expensive real estate — every token must earn its place, and more context can actually hurt if it's irrelevant noise.
Python Example
def calculate_context_budget(
    window_size: int = 128_000,
    system_tokens: int = 500,
    max_output: int = 4_096,
    history_tokens: int = 0,
    retrieved_tokens: int = 0
) -> dict:
    """
    Calculate how much context budget remains for the user query.

    The context window is a FIXED resource shared by ALL components:
      - System prompt (usually fixed per application)
      - Conversation history (grows with each turn)
      - Retrieved documents (RAG chunks, tool results)
      - User's current query
      - Model's output (reserved via max_tokens)

    Returns a dict with budget breakdown and warnings.
    """

    # Step 1: Reserve the non-negotiables first.
    # Output reserve is critical — without it the model's
    # response gets truncated mid-sentence.
    reserved = system_tokens + max_output

    # Step 2: Calculate what's left for dynamic content
    available_for_content = window_size - reserved

    # Step 3: Subtract what's already committed
    used_by_content = history_tokens + retrieved_tokens
    remaining_for_query = available_for_content - used_by_content

    # Step 4: Build the budget report
    budget = {
        "window_size": window_size,
        "system_prompt": system_tokens,
        "output_reserve": max_output,
        "history": history_tokens,
        "retrieved_docs": retrieved_tokens,
        "remaining_for_query": max(0, remaining_for_query),
        "utilization_pct": round(
            (system_tokens + used_by_content + max_output)
            / window_size * 100, 1
        ),
        "warnings": []
    }

    # Step 5: Generate actionable warnings
    if remaining_for_query < 500:
        budget["warnings"].append(
            "CRITICAL: Less than 500 tokens for user query. "
            "Summarize history or reduce retrieved docs."
        )

    if retrieved_tokens > available_for_content * 0.6:
        budget["warnings"].append(
            "Retrieved docs consume >60% of available space. "
            "Consider top-k reduction or chunking."
        )

    if history_tokens > available_for_content * 0.5:
        budget["warnings"].append(
            "History exceeds 50% of budget. "
            "Apply sliding window or summarization."
        )

    return budget

    retrieved_tokens=30_000  # 15 RAG chunks
)

print(f"Remaining for query: {result['remaining_for_query']:,} tokens")

Follow-up Questions
What exactly is "lost in the middle" and how bad is it?
Models recall facts placed at the start and end of the context far more reliably than those in the middle. In benchmark tests, recall for middle-placed facts can drop by 20-40%. The fix is to place your most important context at the boundaries.
Does a larger context window increase latency even if I don't fill it?
Latency scales with actual tokens processed, not the window's maximum size. An 8K prompt in a 128K window costs the same as an 8K prompt in an 8K window. You only pay for what you use.
What is the difference between effective and theoretical context length?
The theoretical limit is the advertised window size. The effective limit is how much context the model can actually use well — typically 60-80% of theoretical before quality degrades. Needle-in-a-haystack benchmarks measure this gap.
How do different models' context windows compare in practice?
GPT-4o supports 128K, Claude 3.5 supports 200K, and Gemini 1.5 Pro supports up to 1M. However, effective recall quality varies — a model with 128K and strong attention may outperform one with 1M and weaker retrieval on practical tasks.

Where the Money Goes

Every LLM API call has multiple cost components. Understanding each helps you optimize the right lever.

Component What It Is Scaling
Input tokensPrompt + system + contextO(n)
Output tokensModel's responseO(n) per token, O(n²) total
AttentionEach token attends to all othersO(n²) compute

ThroughputTokens per second capacityInversely proportional to n

The API price you see (e.g., $3/1M input tokens) bundles these together, but understanding the underlying compute helps explain why output tokens cost more.

Why Output Tokens Cost More

Input tokens are processed in parallel — the entire prompt is fed through the model in one pass. Output tokens are generated sequentially, one at a time, and each new token must attend to all previous tokens. This means:

  • Input: one forward pass, massively parallelizable
  • Output: n forward passes for n output tokens, each increasingly expensive
  • Most providers charge 2-4x more for output than input tokens

This is why controlling max_tokens and asking for structured, concise output is the highest-leverage cost optimization. A response that's 500 tokens instead of 2,000 doesn't just save 4x on output cost — it also reduces latency proportionally. See Topic 2: Token Fertility for how word choice affects token count.

Token-Efficient Prompting

Small changes to prompting style can dramatically reduce token usage:

  • Ask for structured output — JSON with specific fields prevents rambling
  • Set explicit length constraints — "respond in under 100 words"
  • Remove redundancy — saying the same instruction three ways wastes tokens
  • Use references, not repetition — "using the schema above" instead of re-pasting it

For production systems, even a 10% reduction in average tokens per request compounds into significant savings at scale. See Topic 10: Token Budgeting for systematic approaches.

→ Output tokens are 2-4x more expensive than input — controlling max_tokens and response format is the highest-leverage cost optimization.
Python Example
def estimate_cost(
    input_tokens: int,
    output_tokens: int,
    model: str = "gpt-4o"
) -> dict:
    """
    Estimate the cost of an LLM API call.

    Pricing is per-token, but varies by:
      - Model tier (GPT-4o vs Claude 3.5 vs Gemini)
      - Direction (input vs output — output is always more)
      - Caching (some providers discount cached input)

    All prices below are per 1 MILLION tokens.
    """

    # Pricing table: (input_$/1M, output_$/1M)
    # Prices as of late 2024 — check provider docs for current rates
    PRICING = {
        "gpt-4o":          (2.50,  10.00),
        "gpt-4o-mini":     (0.15,   0.60),
        "claude-3.5":      (3.00,  15.00),
        "claude-3-haiku":  (0.25,   1.25),
        "gemini-1.5-pro":  (1.25,   5.00),
    }

    if model not in PRICING:
        raise ValueError(
            f"Unknown model '{model}'. "
            f"Available: {list(PRICING.keys())}"
        )

    in_rate, out_rate = PRICING[model]

    # Cost formula: tokens * (rate / 1,000,000)
    input_cost  = input_tokens  * (in_rate  / 1_000_000)
    output_cost = output_tokens * (out_rate / 1_000_000)
    total_cost  = input_cost + output_cost

    # Latency estimate (rough):
    # - Input processing: ~0.5ms per 1K tokens (parallelized)
    # - Output generation: ~30ms per token (sequential)
    input_latency_ms  = input_tokens * 0.0005 * 1000
    output_latency_ms = output_tokens * 30
    total_latency_ms  = input_latency_ms + output_latency_ms

    return {
        "model": model,
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "input_cost":  round(input_cost, 6),
        "output_cost": round(output_cost, 6),
        "total_cost":  round(total_cost, 6),
        "cost_ratio":  f"Output is {out_rate/in_rate:.1f}x input",
        "est_latency_seconds": round(total_latency_ms / 1000, 1),
    }

Follow-up Questions
How does prompt caching reduce costs?
Providers like Anthropic and Google cache the KV representations of repeated prompt prefixes. If your system prompt is identical across requests, cached input tokens cost 50-90% less. The cache is keyed on exact token sequences from the start of the prompt.
What are practical ways to reduce output tokens?
Set a low max_tokens, request structured output (JSON schemas), add explicit constraints like "respond in under 50 words," and use stop sequences to terminate early. Switching from prose to bullet points alone can cut output tokens by 40%.
Does batching requests save money?
Some providers offer batch APIs at 50% discount (e.g., OpenAI's Batch API). The tradeoff is latency — batch jobs may take hours. For non-real-time workloads like evaluation, classification, or data processing, batching is almost always worth it.
Why is output pricing so much higher than input?
Input tokens are processed in one parallel pass. Output tokens require sequential autoregressive generation — each token needs a full forward pass that attends to all prior tokens. This serial bottleneck makes output 3-10x more compute-intensive per token.

Exceeding the Context

When input overflows the context window, something has to give. Truncate, compress, or selectively retrieve — doing it badly means confident answers from missing evidence.
💡 Overflow is like trying to fit a semester of notes onto one exam cheat sheet — you have to choose what makes the cut.

Context Overflow Strategies

6,000
No strategy selected. All document blocks are sent as-is. When total tokens exceed the context limit, the API will return an error or silently truncate from the end.

Why "Just Use a Bigger Window" Doesn't Work

It's tempting to treat context overflow as a solved problem — just upgrade to a model with a bigger window. But this approach hits three walls:

  • Cost scales linearly — doubling the context doubles the input token cost, and attention compute scales quadratically
  • "Lost in the middle" — as documented in Topic 6: Context Window, models struggle with information buried deep in long contexts
  • Diminishing returns — adding marginally relevant context often degrades answer quality rather than improving it

The right solution is almost always to be smarter about what goes in, not to make the window bigger.

Three Strategies at a Glance

Strategy How Pros Cons
Truncation Cut from end or middle Fast, simple, deterministic Loses potentially critical info
Summarization LLM compresses to gist Preserves all themes Lossy, adds latency & cost
Retrieval Embed & search for relevant chunks Only includes what matters Requires embedding infra

Topic 9: Truncation vs Sliding Windows vs Summarization covers implementation details and production hybrid patterns.

Retrieval-Based Selection

Retrieval-Augmented Generation (RAG) sidesteps the overflow problem entirely by only loading relevant chunks into context. The process:

  • Chunk — split documents into overlapping segments (typically 200-500 tokens)
  • Embed — convert chunks to vectors using an embedding model
  • Search — find the top-k chunks most similar to the user's query
  • Inject — place only those chunks into the context window

The key insight: relevance-based selection means you can work with unlimited source material while only consuming a small, fixed portion of the context window. The tradeoff is that if the embedding model ranks poorly, you'll miss critical context.

→ Retrieval-based selection — picking the most relevant chunks rather than stuffing everything in — almost always outperforms brute-force context filling.
Python Example
from typing import List, Tuple


def strategy_truncate(
    chunks: List[str],
    max_tokens: int,
    count_fn=None
) -> List[str]:
    """
    Strategy 1: Truncation — keep chunks from the start
    until the budget runs out.

    Simple and fast but blind to relevance.
    The last chunks (which may be most recent / important)
    are the first to be dropped.
    """
    if count_fn is None:
        count_fn = lambda t: len(t.split())  # rough proxy

    selected = []
    total = 0
    for chunk in chunks:
        tokens = count_fn(chunk)
        if total + tokens > max_tokens:
            break  # hard cut — everything after this is lost
        selected.append(chunk)
        total += tokens
    return selected


def strategy_summarize(
    chunks: List[str],
    max_tokens: int,
    llm_summarize=None
) -> str:
    """
    Strategy 2: Summarization — compress all chunks into
    a dense summary that fits the budget.

    Preserves themes and key facts, but loses exact
    quotes and details. Adds one LLM call of latency.
    """
    full_text = "\n\n".join(chunks)

    # In production, this calls your LLM with a
    # summarization prompt and a max_tokens constraint
    if llm_summarize:
        return llm_summarize(
            text=full_text,
            instruction=(
                f"Summarize the following into at most "
                f"{max_tokens} tokens, preserving all key "
                f"facts and relationships."
            )
        )

    # Fallback: naive sentence truncation
    sentences = full_text.replace('\n', ' ').split('. ')
    summary = []
    total = 0
    for s in sentences:
        words = len(s.split())
        if total + words > max_tokens:
            break
        summary.append(s)
        total += words
    return '. '.join(summary) + '.'


def strategy_retrieve(
    chunks: List[str],
    query: str,
    max_tokens: int,
    top_k: int = 5,
    embed_fn=None
) -> List[Tuple[str, float]]:
    """
    Strategy 3: Retrieval — embed all chunks, rank by
    similarity to the query, return the top-k that fit.

    Best quality but requires embedding infrastructure.
    Returns (chunk, score) tuples sorted by relevance.
    """
    if embed_fn is None:
        # Toy implementation: keyword overlap scoring
        # In production, use a real embedding model
        query_words = set(query.lower().split())
        def embed_fn(text):
            words = set(text.lower().split())
            overlap = len(query_words & words)
            return overlap / max(len(query_words), 1)

    # Score all chunks
    scored = [(chunk, embed_fn(chunk)) for chunk in chunks]

    # Sort by relevance (highest first)
    scored.sort(key=lambda x: x[1], reverse=True)

    # Take top-k that fit within budget
    selected = []
    total = 0
    for chunk, score in scored[:top_k]:
        tokens = len(chunk.split())
        if total + tokens > max_tokens:
            continue  # skip this chunk, try next
        selected.append((chunk, round(score, 3)))
        total += tokens

    return selected

Follow-up Questions
When is truncation actually the right choice over retrieval?
Truncation works well for chronologically ordered data where recency matters most, like chat history. It's also the only practical option when you can't afford the latency of embedding or summarization, such as real-time streaming applications.
How does hierarchical summarization handle very long documents?
Hierarchical summarization splits a document into sections, summarizes each section independently, then summarizes the summaries. This avoids feeding the entire document through one LLM call and produces more balanced coverage of the content.
What is the map-reduce pattern for context overflow?
Map-reduce sends each chunk to the LLM independently (the "map" step), then combines the individual results in a final "reduce" call. This parallelizes processing across chunks and handles arbitrarily large inputs, though it increases total cost linearly with chunk count.

Three overflow strategies, three tradeoffs — speed vs fidelity vs cost. Most production systems combine all three.
💡 Truncation is a guillotine. Sliding windows are a spotlight scanning a dark room. Summarization is a note-taker who captures the gist but loses the quotes.

When to Use Each

Truncation works when early context is most important and you can afford to lose the tail. Think log analysis where the first entries set the pattern, or document processing where the header matters most.

Sliding windows are the default choice for chatbots and conversational agents. Keep the most recent N turns, discard the oldest. The user's short-term memory is usually focused on recent messages anyway. As described in Topic 8: Exceeding the Context, the key question is how large N should be.

Summarization shines when you need the full arc of a conversation — an agent that's been working on a task for 50 turns needs to remember early decisions even as it executes late steps. The cost is one extra LLM call per summarization cycle.

The Production Hybrid Pattern

Real production systems rarely use a single strategy. The dominant pattern combines all three:

  • Protected zone — system prompt and current user query are never touched
  • Summarized zone — old conversation history gets compressed to a running summary
  • Sliding window — recent turns are kept verbatim in a fixed-size window
  • Retrieved zone — RAG chunks are selected by relevance and inserted

This hybrid approach gives you recency (sliding window), long-term coherence (summary), and factual grounding (retrieval) — all within a fixed budget. Topic 10: Token Budgeting covers how to allocate tokens across these zones.

→ No single strategy wins — production systems summarize old history, retrieve fresh chunks by relevance, and always protect the system prompt and user query from truncation.
Python Example
from typing import List, Optional, Callable


def truncate_history(
    messages: List[dict],
    max_tokens: int,
    count_fn: Callable[[str], int] = None
) -> List[dict]:
    """
    Strategy 1: Truncation — keep messages from the start.

    Simple, zero-cost, but loses the most recent context.
    Typically used with 'keep first + keep last' to protect
    both the system prompt and current query.
    """
    if count_fn is None:
        count_fn = lambda t: len(t.split())

    # Always protect the first (system) and last (user query)
    if len(messages) <= 2:
        return messages

    protected_start = [messages[0]]   # system prompt
    protected_end   = [messages[-1]]  # current query
    middle = messages[1:-1]           # everything else

    budget = max_tokens
    budget -= count_fn(messages[0].get("content", ""))
    budget -= count_fn(messages[-1].get("content", ""))

    # Fill from the start of middle until budget exhausted
    kept = []
    for msg in middle:
        tokens = count_fn(msg.get("content", ""))
        if budget - tokens < 0:
            break
        kept.append(msg)
        budget -= tokens

    return protected_start + kept + protected_end


def sliding_window(
    messages: List[dict],
    max_tokens: int,
    count_fn: Callable[[str], int] = None
) -> List[dict]:
    """
    Strategy 2: Sliding Window — keep the N most recent
    messages that fit within the budget.

    Favors recency, which is usually what matters in
    conversation. Old context is completely lost.
    """
    if count_fn is None:
        count_fn = lambda t: len(t.split())

    # Always keep system prompt
    if not messages:
        return messages

    system = [messages[0]] if messages[0].get("role") == "system" else []
    rest = messages[1:] if system else messages

    budget = max_tokens
    for msg in system:
        budget -= count_fn(msg.get("content", ""))

    # Walk backward from most recent
    kept = []
    for msg in reversed(rest):
        tokens = count_fn(msg.get("content", ""))
        if budget - tokens < 0:
            break
        kept.insert(0, msg)  # maintain order
        budget -= tokens

    return system + kept


def summarize_and_keep_recent(
    messages: List[dict],
    max_tokens: int,
    summary_budget: int = 200,
    recent_turns: int = 4,
    llm_summarize: Optional[Callable] = None,
    count_fn: Callable[[str], int] = None
) -> List[dict]:
    """
    Strategy 3: Summarization — compress old messages into
    a summary, keep recent messages verbatim.

    Best of both worlds: long-term coherence (summary)
    plus short-term fidelity (recent turns).
    The tradeoff is one extra LLM call per cycle.
    """
    if count_fn is None:
        count_fn = lambda t: len(t.split())

    if len(messages) <= recent_turns + 1:
        return messages  # not enough to summarize

    system = [messages[0]] if messages[0].get("role") == "system" else []
    rest = messages[1:] if system else messages

    # Split: old messages to summarize, recent to keep
    old_messages = rest[:-recent_turns]
    recent_messages = rest[-recent_turns:]

    # Build text from old messages for summarization
    old_text = "\n".join(
        f"{m['role']}: {m['content']}" for m in old_messages
    )

    if llm_summarize:
        summary = llm_summarize(
            text=old_text,
            max_tokens=summary_budget
        )
    else:
        # Fallback: naive first-N-words
        words = old_text.split()[:summary_budget]
        summary = " ".join(words) + "..."

    # Inject summary as a system-level context message
    summary_msg = {
        "role": "system",
        "content": (
            f"[Summary of earlier conversation "
            f"({len(old_messages)} messages)]: {summary}"
        )
    }

    return system + [summary_msg] + recent_messages

Follow-up Questions
How do you size the overlap in a sliding window?
Overlap typically ranges from 10-20% of the window size. Too little overlap and the model loses conversational coherence at the boundary. Too much overlap wastes budget on redundant tokens. Start with 2-3 turns of overlap and adjust based on task continuity needs.
What is recursive summarization and when is it needed?
Recursive summarization re-summarizes a summary when it grows too large, creating a cascade of increasingly compressed representations. This is needed for very long interactions (100+ turns) where even a single summary would overflow. Each level loses more detail but preserves the arc.
Can summarization happen incrementally while the conversation is streaming?
Yes — incremental summarization updates the running summary after each turn rather than batch-processing old history. This spreads the LLM cost across turns and avoids a latency spike when the window fills up. The tradeoff is higher total cost due to more frequent, smaller summarization calls.

Budget Rules of Thumb

Effective token budgeting follows a "pay the bills first" philosophy. Here's a priority order that works across most applications:

  • Output reserve (non-negotiable) — always reserve max_tokens first. A truncated response is worse than a slightly shorter context.
  • System prompt (non-negotiable) — your instructions define behavior. Never truncate them.
  • Current query (non-negotiable) — the user's actual request must be included in full.
  • Retrieved context (high priority) — RAG chunks that are directly relevant to the query. As discussed in Topic 6: Context Window, placement matters — put these near the query.
  • Conversation history (flexible) — recent turns matter, old ones can be summarized per Topic 9: Strategies.
  • Examples (flexible) — few-shot examples improve quality but are the first to cut when space is tight.

Common Mistakes

Most token budget failures come from a few recurring anti-patterns:

  • No output reserve — filling 100% of the window with input, leaving no room for the response. The model either errors or produces a truncated, incoherent answer.
  • Static allocations — hardcoding "give 50% to history" regardless of whether there is 50% worth of history. Allocate dynamically based on actual content.
  • Ignoring token fertility — budgeting by word count instead of token count. As Topic 2 shows, the same word count can vary 2-3x in token count depending on language and content type.
  • No monitoring — treating the budget as a one-time design decision. In production, actual usage drifts from estimates as user behavior varies.

Monitoring in Production

Token budgeting is an ongoing operational concern, not a one-time setup. Key metrics to track:

  • p95 input token count — your 95th-percentile request determines whether your budget is realistic
  • Truncation rate — percentage of requests where context had to be reduced. Target: under 5%.
  • Output completion rate — how often does the response hit max_tokens? If frequently, your output reserve is too small.
  • Cost per request distribution — track the spread, not just the mean. A few outlier requests can dominate your bill (Topic 7: Cost & Latency).

Set alerts on these metrics just as you would on latency or error rate. A sudden spike in truncation rate means your users are hitting overflow — and getting worse answers without knowing it.

→ Token budgeting is reliability engineering — treat it like you treat latency monitoring, because overflow failures are just as catastrophic and far less visible.
Python Example
from dataclasses import dataclass, field
from typing import List, Optional, Callable


@dataclass
class TokenBudget:
    """
    A production-grade token budget manager.

    Design philosophy: reserve non-negotiables first,
    then allocate remaining capacity by priority.

    Usage:
        budget = TokenBudget(window_size=128_000)
        budget.set_system_prompt(system_text)
        budget.set_output_reserve(4096)
        budget.add_query(user_query)
        budget.add_history(messages, strategy="sliding")
        budget.add_retrieved(chunks, max_chunks=10)

        final_prompt = budget.build()
        print(budget.report())
    """

    window_size: int = 128_000
    _allocations: dict = field(default_factory=dict)
    _count_fn: Optional[Callable] = None

    def __post_init__(self):
        # Default token counter: ~4 chars per token
        if self._count_fn is None:
            self._count_fn = lambda t: max(1, len(t) // 4)

        # Initialize allocation slots with priorities
        # Lower number = higher priority (never cut)
        self._allocations = {
            "output_reserve": {"tokens": 4096, "priority": 0, "fixed": True},
            "system_prompt":  {"tokens": 0, "priority": 1, "fixed": True, "content": ""},
            "user_query":     {"tokens": 0, "priority": 2, "fixed": True, "content": ""},
            "retrieved":      {"tokens": 0, "priority": 3, "fixed": False, "content": []},
            "history":        {"tokens": 0, "priority": 4, "fixed": False, "content": []},
            "examples":       {"tokens": 0, "priority": 5, "fixed": False, "content": []},
        }

    # --- Setters for each budget zone ---

    def set_system_prompt(self, text: str):
        """Set the system prompt (never truncated)."""
        tokens = self._count_fn(text)
        self._allocations["system_prompt"]["tokens"] = tokens
        self._allocations["system_prompt"]["content"] = text

    def set_output_reserve(self, max_tokens: int):
        """Reserve tokens for the model's response."""
        self._allocations["output_reserve"]["tokens"] = max_tokens

    def add_query(self, text: str):
        """Add the user's current query (never truncated)."""
        tokens = self._count_fn(text)
        self._allocations["user_query"]["tokens"] = tokens
        self._allocations["user_query"]["content"] = text

    def add_history(self, messages: List[dict], strategy: str = "sliding"):
        """
        Add conversation history with overflow strategy.
        Strategies: 'sliding' (keep recent), 'truncate' (keep old).
        """
        remaining = self._remaining_budget()
        kept = []
        total = 0

        if strategy == "sliding":
            # Walk backward, keep most recent first
            for msg in reversed(messages):
                t = self._count_fn(msg.get("content", ""))
                if total + t > remaining:
                    break
                kept.insert(0, msg)
                total += t
        else:
            # Truncate: keep from start
            for msg in messages:
                t = self._count_fn(msg.get("content", ""))
                if total + t > remaining:
                    break
                kept.append(msg)
                total += t

        self._allocations["history"]["tokens"] = total
        self._allocations["history"]["content"] = kept

    def add_retrieved(self, chunks: List[str], max_chunks: int = 10):
        """
        Add RAG chunks, fitting as many as possible
        within the remaining budget.
        """
        remaining = self._remaining_budget()
        kept = []
        total = 0

        for chunk in chunks[:max_chunks]:
            t = self._count_fn(chunk)
            if total + t > remaining:
                continue  # skip, try next (might be smaller)
            kept.append(chunk)
            total += t

        self._allocations["retrieved"]["tokens"] = total
        self._allocations["retrieved"]["content"] = kept

    # --- Budget calculations ---

    def _fixed_cost(self) -> int:
        """Sum of all non-negotiable allocations."""
        return sum(
            a["tokens"] for a in self._allocations.values()
            if a.get("fixed", False)
        )

    def _total_used(self) -> int:
        """Sum of all allocations."""
        return sum(a["tokens"] for a in self._allocations.values())

    def _remaining_budget(self) -> int:
        """Tokens still available for flexible content."""
        return max(0, self.window_size - self._total_used())

    # --- Reporting ---

    def report(self) -> dict:
        """Generate a budget report with warnings."""
        total = self._total_used()
        util = round(total / self.window_size * 100, 1)
        free = self.window_size - total

        warnings = []
        if free < 0:
            warnings.append(f"OVERFLOW by {abs(free):,} tokens!")
        if free < 1000 and free >= 0:
            warnings.append("Less than 1K tokens free — very tight.")
        if self._allocations["output_reserve"]["tokens"] < 1000:
            warnings.append("Output reserve under 1K — risk of truncation.")

        return {
            "window_size": self.window_size,
            "allocations": {
                k: v["tokens"]
                for k, v in self._allocations.items()
            },
            "total_used": total,
            "free": max(0, free),
            "utilization_pct": min(100.0, util),
            "warnings": warnings,
        }


# --- Example usage ---
budget = TokenBudget(window_size=32_000)
budget.set_system_prompt("You are a helpful customer support agent...")
budget.set_output_reserve(2048)
budget.add_query("Why was I charged twice for order #12345?")
budget.add_retrieved([
    "Order #12345 was placed on Jan 5. Payment of $49.99 processed.",
    "Refund policy: duplicate charges are auto-refunded within 48h.",
    "Customer account shows two pending charges of $49.99.",
])
budget.add_history([
    {"role": "user", "content": "I have a billing issue."},
    {"role": "assistant", "content": "I can help with that..."},
])

r = budget.report()
print(f"Utilization: {r['utilization_pct']}%")
print(f"Free tokens: {r['free']:,}")
for w in r["warnings"]:
    print(f"  ⚠ {w}")
Follow-up Questions
How do multi-turn agent loops handle budgets across many iterations?
Agent loops typically use a rolling budget: after each tool call, the agent re-evaluates what fits. Old tool results get summarized, and the most recent result plus the original task description are always preserved. The key constraint is that every iteration must leave enough room for both the next tool call and the final answer.
What metrics should I monitor for token budget health?
Track p95 input tokens, truncation rate, output completion rate (how often responses hit max_tokens), and cost variance across requests. Set alerts when truncation exceeds 5% or when p95 input crosses 80% of your window size.
How does prompt caching interact with token budgets?
Prompt caching (e.g., Anthropic's cache_control) lets you mark stable prefixes that get cached across requests. This doesn't change your token budget — you still use the same window — but it dramatically reduces cost for the cached portion (up to 90% discount) and improves latency.
What does graceful degradation look like for token budgets?
Graceful degradation means progressively dropping lower-priority content rather than failing hard. First cut few-shot examples, then reduce retrieved chunks, then summarize history, and as a last resort truncate. Each step should log a warning so you know quality is being traded for fit.
