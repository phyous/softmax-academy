What Is a Token?

A token is the atomic unit an LLM processes — not a word, not a character, but a statistical building block learned from training data. Every cost, speed, and memory metric in LLMs is measured in tokens.

How Tokenization Actually Works

LLMs never see raw text. Not a single character of your prompt reaches the neural network as a letter or word. Instead, a tokenizer — a completely separate, deterministic algorithm — converts your string into a sequence of integer IDs drawn from a fixed vocabulary. This vocabulary is typically between 32,000 and 100,000 entries, and it is learned during a preprocessing step (not during model training itself) using algorithms like Byte-Pair Encoding (BPE). The resulting integer sequence is the only thing the model ever processes.

Each integer ID maps to a learned embedding vector — a dense array of floating-point numbers, typically ranging from 768 dimensions (small models like BERT-base) to 12,288 dimensions (GPT-4 class models). These vectors are the model's actual input: rich numerical representations that encode semantic meaning, syntactic role, and contextual relationships. The embedding matrix is often one of the largest parameter blocks in the entire model — a 100K vocabulary with 4,096-dimensional embeddings consumes over 400 million parameters just for this lookup table.

  • Token ≠ word. The word "tokenization" typically becomes two tokens: ["token", "ization"]. The word "the" stays as one token: ["the"]. A smiley emoji like 😊 might decompose into 3-4 tokens because its UTF-8 byte representation is multi-byte. This inconsistency is not a bug — it's by design. The tokenizer optimizes for statistical compression, meaning frequently co-occurring byte sequences get merged into single tokens, regardless of whether they align with human word boundaries.
  • Everything downstream is token-denominated. API pricing is quoted as "$X per 1K tokens." Context windows are measured in tokens (128K tokens ≈ roughly 96K English words, but far fewer in code or non-Latin scripts). Inference latency scales with token count because self-attention has O(n²) complexity in the sequence length. Output budgets, rate limits, and caching strategies all operate in token units.
  • Token economy is non-obvious. A "short-looking" JSON payload like {{"name": "Alice", "age": 30}} can cost 3x more tokens than the equivalent natural language "Alice is 30 years old" because every bracket, colon, quote, and whitespace character consumes a token. Similarly, code with heavy indentation and boilerplate is token-expensive relative to its information density.
  • Tokenization determines the model's "resolution." If a concept is expressed in a single token, the model can reason about it atomically. If it requires many tokens, the model must compose understanding across positions — which is harder. This is why rare technical terms, non-English words, and novel proper nouns are often harder for LLMs: they fragment into subword pieces that individually carry less meaning.
  • The vocabulary is frozen after training. Once a tokenizer is trained and a model is built on top of it, the vocabulary cannot be changed without retraining the entire model. This is why models trained in 2022 may tokenize "ChatGPT" awkwardly (splitting it into subwords) even though it became a common term — it was not frequent enough in the tokenizer's training data to earn its own token.
Python Example 
# ---------------------------------------------------------------
# Tokenization with tiktoken — OpenAI's fast BPE tokenizer
# tiktoken is the tokenizer behind GPT-3.5, GPT-4, and GPT-4o.
# It converts raw text into integer IDs from a fixed vocabulary.
# ---------------------------------------------------------------

import tiktoken  # OpenAI's open-source tokenizer library

# Load the cl100k_base encoding — this is the tokenizer used by
# GPT-4 and GPT-3.5-turbo. It has ~100K vocabulary entries.
# Different models use different encodings (e.g., o200k_base for GPT-4o).
enc = tiktoken.encoding_for_model("gpt-4")

# The text we want to tokenize — a simple English sentence
text = "Tokenization splits text into subword units."

# encode() converts the string into a list of integer token IDs.
# Each integer maps to one entry in the tokenizer's vocabulary.
# This is the ACTUAL input the neural network receives.
tokens = enc.encode(text)

# Print the raw integer IDs — these are what the model sees
print("Token IDs:", tokens)
# Output: [5765, 2065, 45, 25, 1495, 1495, ...]

# decode_single_token_bytes() reveals the text each ID represents.
# We decode each token individually to see the subword splits.
# Notice: some tokens include leading spaces (the "Ġ" convention).
for t in tokens:
    # Convert byte representation back to readable string
    decoded = enc.decode_single_token_bytes(t).decode("utf-8", errors="replace")
    print(f"  ID {t:6} → '{decoded}'")

# Count tokens — critical for cost estimation and context management.
# GPT-4 charges ~$0.03/1K input tokens, so this directly affects cost.
print(f"\nTotal tokens: {len(tokens)}")

# Calculate the chars-per-token ratio — English averages ~4 chars/token.
# Code and JSON are lower (~2-3). Chinese/Japanese can be ~1.5.
ratio = len(text) / len(tokens)
print(f"Chars per token: {ratio:.1f}")

# Roundtrip: decode the token IDs back to the original text.
# A correct tokenizer guarantees lossless roundtripping.
reconstructed = enc.decode(tokens)
assert reconstructed == text  # This must always pass — tokenization is lossless
print(f"Roundtrip OK: '{reconstructed}'")
Follow-up Questions
How does vocabulary size affect model performance?
Larger vocabularies mean more common words and phrases get single tokens, which leads to shorter sequences (faster inference, lower cost per request) and lets the model treat frequent concepts atomically. However, the embedding matrix grows linearly with vocab size — a 100K vocab with 4096-dim embeddings is 400M parameters just for the lookup table. This increases memory requirements and slows down the softmax computation over the output vocabulary. Most modern LLMs settle on 32K-100K tokens as a sweet spot. GPT-2 used 50,257; LLaMA uses 32,000; GPT-4o jumped to 200,000 for better multilingual coverage. Too small a vocabulary causes excessive fragmentation (the word "unfortunately" might become 4+ tokens), making sequences longer and inference slower. Too large a vocabulary wastes parameters on extremely rare tokens that the model rarely encounters during training, meaning those embedding rows are poorly learned and essentially dead weight.
Why do different models tokenize the same text differently?
Each model family trains its own tokenizer on its own training corpus, and the tokenizer's merge rules are determined entirely by the statistical frequencies in that corpus. GPT-4 uses cl100k_base (trained on a mix of English web text, code, and multilingual data), while LLaMA uses a SentencePiece tokenizer trained on a different data mix. Because the underlying corpora differ, the learned merge sequences differ, and therefore the same input text produces different token sequences. Additionally, design choices matter: some tokenizers are byte-level (can handle any input), some apply NFKC normalization (folding characters), and some add special whitespace handling. This is why you should never assume token counts transfer across models — a prompt that fits in GPT-4's 8K context might exceed a different model's limit after re-tokenization.
What happens when a tokenizer encounters text it has never seen?
Modern byte-level tokenizers (like those used in GPT-3.5+ and LLaMA) literally cannot encounter an "unknown" input — they fall back to individual bytes. If a word is extremely rare and was never merged during BPE training, it simply gets split into its constituent bytes (or characters), each of which has its own token ID. This is a fundamental advantage over older word-level vocabularies (like early Word2Vec or GloVe) which had a special [UNK] token for unknown words, losing all information about the word's content. With byte-level BPE, the word "supercalifragilistic" would be split into recognizable subwords even if it never appeared in training data, and the model can still reason about it using the meanings of those subwords. The downside is that very novel strings (random hashes, base64 blobs, invented words) consume many tokens because they decompose to individual bytes.
How is whitespace handled in tokenization?
Whitespace handling is one of the trickiest aspects of tokenization and varies significantly across tokenizers. GPT-style tokenizers (using tiktoken) typically prepend a space character to the beginning of each word-initial token, so the token for " the" (with a leading space) is different from "the" (without). This means spaces are absorbed into the token that follows them, rather than being separate tokens. SentencePiece uses a different convention: it replaces spaces with a special Unicode character (▁, U+2581) before tokenization, making whitespace explicitly visible in the vocabulary. Newlines, tabs, and multiple spaces all behave differently — a line of Python indentation (4 spaces) might be a single token in a code-optimized tokenizer but 4 separate tokens in a text-optimized one. This is why code-specific models often have special tokens for common indentation patterns. The practical implication: formatted text (markdown, code, JSON) can be surprisingly token-expensive because of how whitespace is tokenized.

Why Tokens and Words Diverge

The word "word" feels intuitive — it is what sits between spaces. But this human-centric definition breaks down almost immediately when you throw real-world text at a tokenizer. Consider the word "unhappiness": a human sees one word, but a BPE tokenizer sees three meaningful pieces — ["un", "happi", "ness"] — because those subword fragments appear frequently across the training corpus and each carries morphological meaning. This decomposition is a feature: it lets the model reuse the "un-" prefix across "undo", "unlikely", "uncertain" etc., sharing learned semantics across related words.

Fertility (tokens per word) is a critical concept for multilingual fairness and cost. English text typically has a fertility of 1.0-1.3 with modern tokenizers, meaning most English words map to roughly one token. But languages like Hindi, Thai, or Amharic can have fertilities of 3-8x, meaning a sentence that costs $0.001 in English might cost $0.005 in Hindi — not because the model is biased, but because the tokenizer was trained on predominantly English data, so English byte sequences got more aggressive merging. This is an active area of research: GPT-4o's 200K vocabulary was partly motivated by reducing fertility disparities across languages.

  • Common English words are typically single tokens because they appear billions of times in training data, earning their own vocabulary entries. Words like "the", "and", "is" are always single tokens.
  • Rare or compound words decompose into subword pieces. "Cryptocurrency" might split into ["Crypt", "ocurrency"] or ["Crypto", "currency"] depending on the tokenizer. The exact split depends on which byte-pair merges were learned.
  • Code is token-expensive because programming syntax includes many short, distinct characters (brackets, operators, semicolons) that each consume a token. A Python function definition def calculate_average(nums): might be 2-3 "words" but 8-10 tokens.
  • Structured data (JSON, XML, YAML) has the worst token economy because structural characters dominate. The JSON {{"a": 1}} is 7 tokens despite conveying almost no information — nearly every character is a delimiter that needs its own token.
  • Multilingual text varies dramatically. Languages with Latin scripts and spaces (Spanish, French) behave similarly to English. Languages without spaces (Chinese, Japanese, Thai) or with rich morphology (Turkish, Finnish) tend to have much higher fertility, meaning more tokens per unit of meaning.

# Comparing word count vs. token count across different inputs
# This demonstrates WHY token-based pricing feels uneven —
# some text types are far more token-expensive than others.
# ---------------------------------------------------------------

import tiktoken  # OpenAI's BPE tokenizer

# Use GPT-4's encoding to get accurate token counts
enc = tiktoken.encoding_for_model("gpt-4")

# Test cases: same "amount of information", very different token costs
samples = {
    "English prose": "The quick brown fox jumps over the lazy dog",
    "Morphology":    "unhappiness, unbelievable, preprocessing",
    "Python code":   "def calculate_average(nums): return sum(nums)/len(nums)",
    "JSON payload":  '{"users": [{"name": "Alice", "age": 30}]}',
    "URL":           "https://api.example.com/v2/users?limit=50&offset=100",
}

# Analyze each sample to reveal token economy differences
for label, text in samples.items():
    # Split on whitespace for naive word count
    words = text.split()
    # Tokenize to get the actual token sequence the model sees
    tokens = enc.encode(text)

    # "Fertility" = tokens per word. Higher = more expensive per word.
    # English prose: ~1.0. JSON: ~3-5. URLs: ~10+.
    fertility = len(tokens) / max(1, len(words))

    print(f"\n{label}:")
    print(f"  Text:      {text}")
    print(f"  Words:     {len(words)}")
    print(f"  Tokens:    {len(tokens)}")
    print(f"  Fertility: {fertility:.1f}x")

    # Show the actual token breakdown so you can see the splits
    # This reveals WHERE the tokenizer draws its boundaries
    decoded = [enc.decode([t]) for t in tokens]
    print(f"  Splits:    {decoded}")

# Key insight: A JSON payload with 3 key-value pairs uses more tokens
# than a full English sentence with 9 words. Structured data is expensive!
Follow-up Questions
Why do some languages cost 3-5x more per API call than English?
Tokenizer vocabularies are built from training data, and most large-scale training corpora are heavily English-dominated (often 60-80% English by volume). During BPE training, English byte sequences get merged aggressively because they appear most frequently, resulting in longer, more efficient tokens for English text. A common English word like "computer" is one token, but its Hindi equivalent "कंप्यूटर" might be 3-5 tokens because the Devanagari byte sequences were merged less aggressively. Since API pricing is per-token, the same semantic content costs 3-5x more in Hindi. This is a recognized fairness problem. GPT-4o addressed it partially by increasing vocabulary size to 200K and training the tokenizer on a more multilingual corpus, reducing fertility gaps by 30-50% for many languages. However, parity hasn't been achieved — some languages like Burmese or Khmer still have 5-8x higher fertility than English.
How can I write prompts to be more token-efficient?
Several practical strategies help reduce token consumption without losing meaning. First, prefer natural language over structured formats: "Alice is 30 years old" is fewer tokens than {"name":"Alice","age":30}. Second, avoid excessive whitespace and formatting — markdown headers, bullet points, and indentation all consume tokens. Third, use common English words over rare technical jargon (common words are usually single tokens; rare words fragment). Fourth, be concise: remove filler phrases like "I would like you to" or "Could you please." Fifth, for few-shot prompting, use the minimum number of examples that achieves good performance — each example adds its full token cost. Sixth, leverage system prompts and caching: if you repeat the same instructions across many requests, a cached system prompt is billed at reduced rates. For structured output, ask the model to return compact formats (CSV or TSV) instead of verbose JSON.
How does tokenizer-aware chunking improve RAG systems?
In Retrieval-Augmented Generation (RAG) systems, documents must be split into chunks that fit within the model's context window. Naive chunking strategies split by character count or word count, but neither aligns with the model's actual token budget. A 512-word chunk might be 500 tokens (for clean English prose) or 1,200 tokens (for code-heavy documentation), making context window utilization unpredictable. Tokenizer-aware chunking counts actual tokens instead, ensuring each chunk uses a predictable fraction of the context window. This has three benefits: (1) you can reliably fit N chunks into a prompt without risking truncation, (2) you maximize information density per request since no token budget is wasted, and (3) you avoid splitting mid-token, which can happen when character-based splitting cuts a multi-byte character sequence. Libraries like LangChain and LlamaIndex offer TokenTextSplitter classes that use the model's actual tokenizer for boundary detection, typically with configurable overlap to preserve context across chunk boundaries.

The BPE Algorithm, Explained From Scratch

Before BPE, NLP models used word-level vocabularies: a fixed dictionary of, say, 50,000 known words. Any word not in that dictionary was replaced with a special [UNK] (unknown) token, losing all information about what the word actually was. This was a catastrophic problem — imagine a medical NLP system that replaces "acetaminophen" with [UNK] simply because it did not appear in the training corpus. The model cannot distinguish it from any other unknown word.

BPE solved this elegantly by working at the subword level. The algorithm is surprisingly simple:

  • Step 0 — Initialize with characters. Start with a vocabulary containing every individual character (byte) that appears in the training corpus, plus a special end-of-word marker. So the initial vocabulary might be {a, b, c, ..., z, _, </w>}. Every word in the corpus is represented as a sequence of these characters.
  • Step 1 — Count all adjacent pairs. Scan the entire corpus and count how many times each pair of adjacent symbols appears. For example, in the corpus "low low lower newest", the pair ("l", "o") appears 3 times, ("o", "w") appears 3 times, ("e", "s") appears 2 times, etc.
  • Step 2 — Merge the most frequent pair. Take the pair with the highest count and replace every occurrence of that pair with a new single symbol. If ("e", "s") is the most frequent, then every "e s" in the corpus becomes "es", and "es" is added to the vocabulary.
  • Step 3 — Repeat. Go back to Step 1 and repeat. Each iteration adds one new symbol to the vocabulary and reduces the total number of symbols in the corpus by the count of the merged pair. Continue until you reach your desired vocabulary size (e.g., 50,000 merges).
  • Why it works: Common substrings are merged first, giving them compact single-token representations. Rare substrings remain decomposed into smaller pieces. This means the model can ALWAYS represent ANY input — worst case, it falls back to individual bytes. The [UNK] problem is eliminated entirely.
  • Vocabulary size is a hyperparameter. You choose how many merges to perform. More merges = larger vocabulary = shorter sequences (each token covers more text) but more parameters in the embedding matrix. GPT-2 used 50,257 merges; GPT-4 used ~100,000; GPT-4o used ~200,000. The optimal size depends on the training data diversity, target languages, and memory budget.
  • Byte-level BPE (used by GPT-2 and successors) operates on raw bytes (0-255) instead of Unicode characters. This guarantees coverage of ANY input — emojis, binary data, any script — because every possible file is a sequence of bytes. The initial vocabulary is just 256 entries (one per byte value), and everything else is built through merges.
  • Which models use BPE? Most GPT-family models (GPT-2, GPT-3, GPT-4, GPT-4o), RoBERTa, and BART use BPE. LLaMA and T5 use SentencePiece (covered in Topic 4), which can run either BPE or a unigram algorithm. BERT uses a related algorithm called WordPiece, which is similar to BPE but uses a slightly different scoring metric for choosing which pair to merge.
Python Example 
# ---------------------------------------------------------------
# A minimal BPE implementation from scratch
# This shows exactly how the algorithm builds a vocabulary
# by iteratively merging the most frequent character pairs.
# Real tokenizers (tiktoken, HuggingFace) do the same thing
# but with heavy optimization for speed.
# ---------------------------------------------------------------

from collections import Counter  # For efficiently counting pair frequencies

def get_pairs(tokens):
    """Count every adjacent pair of symbols in the corpus.
    Returns a Counter mapping (symbol1, symbol2) -> frequency.
    This is the 'statistics gathering' step of BPE."""
    pairs = Counter()
    for word, freq in tokens.items():
        symbols = word.split()  # Split word into current symbols
        # Slide a window of size 2 across the symbol sequence
        for i in range(len(symbols) - 1):
            # Weight by word frequency — common words matter more
            pairs[(symbols[i], symbols[i+1])] += freq
    return pairs

def merge_pair(pair, tokens):
    """Replace every occurrence of (a, b) with the merged 'ab'.
    This is the core merge operation — it modifies the corpus
    in-place by joining the most frequent pair into one symbol."""
    new_tokens = {}
    bigram = ' '.join(pair)  # e.g., "e s" — what we're looking for
    replacement = ''.join(pair)  # e.g., "es" — what we replace it with
    for word, freq in tokens.items():
        # Replace the spaced pair with the merged version
        new_word = word.replace(bigram, replacement)
        new_tokens[new_word] = freq
    return new_tokens

# Our training corpus — each word split into characters with end marker
# The numbers represent word frequencies in the corpus
# "low" appears 5 times, "lower" 2 times, etc.
corpus = {
    "l o w </w>": 5,      # "low"   — very common
    "l o w e r </w>": 2,  # "lower" — shares prefix with "low"
    "n e w e s t </w>": 6,  # "newest" — most frequent
    "w i d e s t </w>": 3,  # "widest" — shares suffix with "newest"
}

# Track the merge rules we learn — these define the tokenizer
merge_rules = []

# Perform 10 BPE merge iterations
# Each iteration: find best pair, merge it, record the rule
for i in range(10):
    pairs = get_pairs(corpus)
    if not pairs:
        break  # No more pairs to merge — corpus fully compressed

    # Select the pair with highest frequency — this is the greedy choice
    # that makes BPE a greedy compression algorithm
    best = max(pairs, key=pairs.get)

    # Apply the merge across the entire corpus
    corpus = merge_pair(best, corpus)

    # Record this merge rule — during tokenization, we replay these
    # rules in order to tokenize new, unseen text
    merge_rules.append(best)

    print(f"Step {i+1}: Merge '{best[0]}' + '{best[1]}' (freq={pairs[best]})")
    print(f"  Corpus: {corpus}\n")

# The merge_rules list IS the tokenizer — it's saved to disk and used
# at inference time to tokenize any new input text.
print("Learned merge rules:", merge_rules)
Follow-up Questions
What is byte-level BPE and why did GPT-2 introduce it?
Traditional BPE operates on Unicode characters, which means the initial vocabulary needs one entry for every unique character in the training data. For multilingual text, this can be tens of thousands of characters before any merging even begins, and some rare Unicode characters might never appear in training at all. Byte-level BPE, introduced with GPT-2, operates on raw bytes instead — the initial vocabulary is exactly 256 entries (one per byte value from 0x00 to 0xFF). Since every possible text file is ultimately a sequence of bytes, this guarantees that the tokenizer can handle ANY input, including emojis, rare scripts, binary data, or even corrupted text. The tradeoff is that non-ASCII characters require multiple bytes (UTF-8 encoding), so a single Chinese character might start as 3 byte-tokens before merges compress it. In practice, after enough merges, common multi-byte sequences get merged into single tokens anyway, so the efficiency converges with character-level BPE for well-represented languages.
How do you choose the right vocabulary size?
Vocabulary size is a tradeoff between sequence compression and model size. A larger vocabulary means common phrases get single tokens, producing shorter sequences — this speeds up inference (fewer attention computations) and reduces API costs. But the embedding matrix has shape (vocab_size x hidden_dim), so a 200K vocabulary with 4096-dim embeddings uses 800M parameters just for embeddings. For small models, this can be a disproportionate fraction of total parameters. Empirically, 32K works well for primarily English models (LLaMA, Mistral). 50K-100K is the sweet spot for English + code + some multilingual (GPT-3/4). 200K+ targets broad multilingual coverage (GPT-4o). Research shows diminishing returns past 100K for English-only tasks, but multilingual fertility ratios improve significantly up to 200K+. Some researchers suggest the "optimal" vocab size scales with the square root of the training data size.
How does BPE differ from the unigram language model approach?
BPE is a bottom-up greedy algorithm: it starts with characters and iteratively ADDS merges. The unigram model (used by SentencePiece) works top-down: it starts with a LARGE initial vocabulary (often 1M+ candidates) and iteratively REMOVES tokens whose removal would least increase the overall corpus encoding loss. At each step, unigram computes the probability of every possible segmentation of every word and prunes the least useful tokens. This gives unigram a key advantage: it can explore multiple segmentations of the same word probabilistically, while BPE is locked into one deterministic segmentation path. Unigram also enables "subword regularization" — during training, you can sample different valid tokenizations of the same text, which acts as data augmentation and improves robustness. BPE's advantage is simplicity and speed — both in training and inference. In practice, the quality differences between BPE and unigram are modest for most tasks, which is why both remain widely used.
Can BPE merges cross word boundaries?
In the standard BPE formulation, no — a pre-tokenization step splits the text into words first (typically by whitespace and punctuation), and BPE merges only happen within word boundaries. This prevents the tokenizer from creating tokens like "the_cat" that span two words, which would be harmful because it would make the vocabulary extremely sparse and context-dependent. However, the definition of "word boundary" varies. GPT-2 uses a regex-based pre-tokenizer that splits on spaces, punctuation, and case transitions, so "New York" is two pre-tokens and can never merge into one. SentencePiece, by contrast, treats the input as a raw character/byte stream and uses a special whitespace character (▁), which CAN be part of a token — so "▁the" is a single token. This is not truly "crossing" a word boundary, but rather encoding the boundary marker into the token itself. Some experimental tokenizers do allow cross-word merges for common multi-word expressions, but this is not standard practice.

Why Whitespace Assumptions Break Everything

Most tokenization pipelines (including the one used by GPT-2) begin with a pre-tokenization step that splits the input on whitespace and punctuation. This produces a list of "words" which are then individually processed by BPE or another subword algorithm. For English, this works beautifully — words are neatly separated by spaces. But for a huge fraction of the world's languages, this assumption is catastrophically wrong.

Japanese uses three writing systems (hiragana, katakana, kanji) and does not use spaces between words at all. The sentence "東京は日本の首都です" has no spaces, so a whitespace-based pre-tokenizer treats the entire sentence as a single "word" — an absurdly long symbol that will fragment into dozens of individual characters during BPE, wasting tokens. Thai has the same problem: "กรุงเทพมหานคร" (Bangkok) is written without spaces between syllables. Chinese, Lao, Khmer, and many other scripts share this characteristic. Even in languages that DO use spaces, like Arabic, the complex morphology means a single "word" can encode what English expresses as an entire phrase.

SentencePiece, developed by Google in 2018, solves this by treating the input as a raw byte or character stream with no pre-tokenization step. Spaces are not treated as boundaries — instead, they are replaced with a special Unicode meta-character (▁, U+2581) and included in the vocabulary learning process just like any other character. This means SentencePiece can learn tokens that CROSS what would be word boundaries in English, and it can learn to segment languages that have no word boundaries at all.

  • Language-agnostic by design. Because SentencePiece never assumes the input has spaces, it works identically on English, Japanese, Thai, Arabic, code, and even mixed-language text. You feed it raw text, and it figures out the optimal subword segmentation purely from statistical patterns. This is why it became the default tokenizer for multilingual models.
  • The .model file is self-contained and portable. Unlike tiktoken (which requires the merge rules file) or HuggingFace tokenizers (which need a tokenizer.json plus a vocabulary file), SentencePiece packs everything — vocabulary, merge rules, normalization settings, and special token definitions — into a single binary .model file. This makes deployment trivial: ship one file, and any platform that can load SentencePiece can tokenize identically, regardless of programming language or OS.
  • BPE vs. Unigram mode. SentencePiece supports two algorithms: BPE (same bottom-up merging as Topic 3) and unigram (a top-down probabilistic approach that starts with a large vocabulary and prunes). The unigram mode enables subword regularization — during training, each input can be tokenized in multiple valid ways, which acts as data augmentation and makes the model more robust to unusual tokenizations at inference time. T5 and mBART use SentencePiece in unigram mode; LLaMA and Mistral use it in BPE mode.
  • NFKC normalization. By default, SentencePiece applies Unicode NFKC normalization, which folds visually similar characters into canonical forms (e.g., full-width "Ａ" → "A", ligature "ﬁ" → "fi"). This reduces vocabulary sparsity but can cause subtle bugs if your application relies on preserving exact Unicode codepoints. You can disable normalization during training, and some models (like LLaMA) do.

# Unlike tiktoken, SentencePiece doesn't assume spaces separate words.
# It treats the input as a raw stream, making it ideal for
# Japanese, Chinese, Thai, and other non-space-delimited languages.

# ---- TRAINING: Build a tokenizer from raw text ----
# Unlike tiktoken (which ships pre-trained), SentencePiece lets you
# train your OWN tokenizer on your own data. This is how LLaMA,
# T5, and Mistral built their tokenizers.

spm.SentencePieceTrainer.train(
    input="training_corpus.txt",       # Raw text file — no preprocessing needed
    model_prefix="my_tokenizer",       # Output: my_tokenizer.model + .vocab
    vocab_size=8000,                   # Target vocabulary size — 8K for demo, 32K+ for production
    model_type="bpe",                  # Algorithm: "bpe" or "unigram" (T5 uses unigram)
    character_coverage=0.9995,        # What fraction of characters to cover (0.9995 = keep 99.95%)
    normalization_rule_name="nfkc",   # Unicode normalization: folds Ａ→A, ﬁ→fi, etc.
    pad_id=3,                          # Reserve ID 3 for [PAD] — used for batch padding
    unk_id=0,                          # Reserve ID 0 for [UNK] — fallback for uncovered chars
    bos_id=1,                          # Reserve ID 1 for [BOS] — beginning of sequence
    eos_id=2,                          # Reserve ID 2 for [EOS] — end of sequence
)

# ---- LOADING: Use the trained model for tokenization ----
# The .model file is completely self-contained — it includes the
# vocabulary, merge rules, and normalization settings.
sp = spm.SentencePieceProcessor()
sp.load("my_tokenizer.model")  # Load the binary model file

# ---- TOKENIZATION: Works on any language without modification ----
# The key insight: SentencePiece doesn't split on spaces first.
# It processes raw bytes, so Japanese works just as well as English.

texts = [
    "Machine learning is transforming AI",  # English — spaces between words
    "機械学習はAIを変革しています",            # Japanese — NO spaces at all
    "การเรียนรู้ของเครื่อง",                    # Thai — no spaces between words
]

for text in texts:
    # encode_as_pieces() returns subword strings (human-readable)
    # Notice: ▁ (underscore) marks where spaces WERE in the input
    pieces = sp.encode_as_pieces(text)

    # encode_as_ids() returns integer IDs (what the model actually uses)
    ids = sp.encode_as_ids(text)

    print(f"\nInput:  {text}")
    print(f"Pieces: {pieces}")    # e.g., ['▁Machine', '▁learning', ...]
    print(f"IDs:    {ids}")       # e.g., [1234, 5678, ...]

    # Verify lossless roundtrip — decode must recover original text
    decoded = sp.decode_pieces(pieces)
    assert decoded == text  # SentencePiece guarantees lossless encoding
Follow-up Questions
When should I use SentencePiece vs. tiktoken?
Use tiktoken when you're working with OpenAI models (GPT-3.5, GPT-4, GPT-4o) — it's their official tokenizer and gives you exact token counts for cost estimation and context window management. Use SentencePiece when you're working with open-weight models like LLaMA, Mistral, or T5, as these models ship with SentencePiece .model files. If you're training your OWN model from scratch, SentencePiece is generally preferred because: (1) it lets you train a tokenizer on your specific data, (2) it handles multilingual text without external word segmenters, (3) the .model file is easy to distribute, and (4) it supports both BPE and unigram algorithms. Tiktoken is faster at inference (it's written in Rust) but doesn't support training custom tokenizers — you can only use OpenAI's pre-trained encodings.
What does NFKC normalization do and when should I disable it?
NFKC (Normalization Form Compatibility Composition) is a Unicode standard that maps visually similar characters to a single canonical form. For example: full-width "Ａ" (used in Japanese text) becomes "A", the ligature "ﬁ" becomes "fi", superscript "²" becomes "2", and various dash characters (en-dash, em-dash) may be folded together. This reduces vocabulary sparsity because the tokenizer doesn't need separate entries for "A" and "Ａ". However, NFKC can cause problems when exact Unicode preservation matters — for example, in code where full-width characters are syntactically distinct, in mathematical notation where superscripts carry meaning, or in text processing pipelines where byte-exact roundtripping is required. LLaMA disables NFKC normalization for this reason. You can control it during SentencePiece training with the normalization_rule_name parameter: set it to "identity" to skip all normalization.
Can I add custom pre-tokenization rules to SentencePiece?
Yes, but with caveats. SentencePiece supports custom normalization rules through a TSV file format (--normalization_rule_tsv flag during training) where you can define character-level mappings. You can also use the --split_by_whitespace=false flag (the default) to prevent whitespace-based pre-splitting, or set it to true if you want English-style word boundaries. For more complex pre-tokenization (like separating digits, splitting on punctuation, or handling code syntax), you'd typically preprocess the text BEFORE passing it to SentencePiece, then post-process the output to undo any artifacts. Some model developers (like the LLaMA team) added custom regex-based pre-tokenization on top of SentencePiece to get finer control over how code, numbers, and whitespace are handled. The HuggingFace tokenizers library wraps SentencePiece and lets you compose a pre-tokenizer, the core model, and a post-processor into a configurable pipeline.

Special Tokens

Special tokens are invisible structural markers — [BOS], [EOS], [SEP], [PAD] — that tell the model where sequences start, end, and transition. Mishandle them and the model misinterprets everything.

The Invisible Scaffolding of Language Models

When you type a message into ChatGPT or call an API, you see a simple conversation: your message, the model's response. But underneath, the model sees something radically different — a carefully structured sequence of tokens where special, non-textual markers delineate where things start, stop, and transition. These special tokens are never shown to the user, but they are absolutely critical for the model's understanding of the input structure.

Think of special tokens as punctuation for the model's attention mechanism. Just as a period tells a human reader "this sentence is done," an [EOS] token tells the model "this sequence is complete — stop generating." Without these markers, the model would have no way to distinguish between "the system prompt ends here and the user's message begins" versus "this is all one continuous stream of text." The model was trained with these markers present in every single training example, so removing or misplacing them causes the model to behave as if the input is malformed or belongs to a different distribution than what it learned.

If the base model expects <|im_start|>system\n...<|im_end|> but your fine-tuning data uses [INST]...[/INST], the model receives conflicting structural signals. It may appear to "work" during training (the loss decreases) but produce subtly broken outputs: hallucinated role transitions, failure to follow system prompts, or inconsistent stopping behavior. Always check the model card for the exact chat template.
  • ChatML is a de facto standard for chat models. OpenAI's ChatML format wraps each message in <|im_start|>role\n...<|im_end|>\n markers. LLaMA uses [INST]...[/INST]. Mistral uses <s>[INST]...[/INST]. Anthropic uses \n\nHuman:...\n\nAssistant:. These formats are NOT interchangeable — using the wrong format for a given model is like speaking French to someone who only understands Japanese. The HuggingFace apply_chat_template() method handles this automatically by reading the template from the model's tokenizer config.
  • Attention masks and special tokens interact critically. When you batch multiple sequences together, shorter sequences are padded with [PAD] tokens. The attention mask must be set to 0 for padding positions, telling the model to ignore them entirely. If you forget to set the attention mask, the model attends to padding tokens as if they were meaningful content, which degrades output quality — sometimes subtly (slightly worse accuracy), sometimes catastrophically (completely incoherent output). Some models use [EOS] as the padding token (GPT-2 does this), which can cause confusion if you're not careful.
  • Special tokens have dedicated IDs that bypass normal tokenization. Unlike regular tokens, special tokens are added to the vocabulary explicitly — they are not learned through BPE merges. When you call tokenizer.encode("[BOS]"), the tokenizer does NOT treat the brackets and letters as regular characters. Instead, it recognizes the entire string as a special token and maps it directly to its reserved ID. This is handled by the add_special_tokens parameter in HuggingFace: tokenizer.encode(text, add_special_tokens=True) automatically prepends/appends the appropriate markers.
  • Model-family differences in special tokens cause real production bugs. A common failure mode: you download a model and tokenizer separately, and they come from slightly different versions. The model expects token_id=1 to be [BOS], but the tokenizer maps [BOS] to token_id=0. The result is that every input starts with the wrong token, and model quality degrades in hard-to-debug ways. Always load the model and tokenizer from the same checkpoint, and verify with tokenizer.bos_token_id, tokenizer.eos_token_id, etc.

Follow-up Questions
How do I debug special token mismatches when fine-tuning?
Special token mismatches are insidious because the model often appears to work but produces subtly degraded output. Here's a systematic debugging approach: (1) Always load the tokenizer from the same checkpoint as the model, never from a different version. (2) Print tokenizer.all_special_tokens and compare against the model card's documentation. (3) Encode a known chat template with skip_special_tokens=False and manually inspect the decoded output — you should see the special tokens exactly where you expect them. (4) Check tokenizer.bos_token_id, eos_token_id, pad_token_id against the model's config.json — they must match. (5) If you see your model generating text beyond where it should stop, the EOS token is likely wrong. If it ignores system prompts, the chat template markers are wrong. (6) Use tokenizer.apply_chat_template(messages, tokenize=False) to see the raw formatted string, then verify it matches examples from the model's documentation. (7) When in doubt, use the exact training code and data format from the model's official repository.
What is ChatML and why are there so many chat formats?
ChatML (Chat Markup Language) is OpenAI's format for structuring multi-turn conversations. Each turn is wrapped in <|im_start|>role\ncontent<|im_end|> tags. The proliferation of competing formats (LLaMA's [INST]/[/INST], Anthropic's Human:/Assistant:, Mistral's <s>[INST], Vicuna's USER:/ASSISTANT:) happened because chat-tuning was developed independently by different teams with no coordination. Each team chose whatever format was convenient for their training pipeline. This is a genuine interoperability problem — you cannot take training data formatted for LLaMA and use it with a ChatML model without reformatting. The HuggingFace tokenizers library partially solves this by storing the chat template in the tokenizer's config and providing apply_chat_template(), but there's still no universal standard. The closest thing to a standard is the OpenAI messages API format (list of role/content dicts), which most libraries can convert TO the model-specific format automatically.
How do attention masks interact with special tokens like [PAD]?
When you batch multiple sequences of different lengths, shorter sequences are padded with [PAD] tokens to make all sequences the same length. The attention mask is a binary tensor (same shape as the input IDs) where 1 means "attend to this token" and 0 means "ignore this token." All [PAD] positions should have attention_mask=0, preventing the model from incorporating padding into its representations. Without proper masking, the model treats [PAD] tokens as meaningful input, which: (1) dilutes attention scores across irrelevant positions, (2) corrupts the hidden states with padding embeddings, and (3) can cause the model to generate padding-like output. Some models are more sensitive to this than others — decoder-only models (GPT, LLaMA) with causal attention are somewhat robust because each position only attends to previous positions, but encoder models (BERT) and encoder-decoder models (T5) are highly sensitive. Additionally, the attention mask interacts with positional encodings: if padding is on the LEFT (left-padding), the positional encoding for the first real token is offset, which some models handle poorly. LLaMA and GPT models expect left-padding for generation tasks but right-padding for training — getting this wrong can cause significant quality degradation.

Context Window

The context window is the model's working desk — everything it can see at once. System prompt, user input, retrieved docs, and the model's own output all compete for the same fixed space.

What Is a Context Window, Really?

The context window is not memory in any human sense. It is the attention scope of the transformer — the set of tokens the model can attend to when producing the next token. Think of it as RAM, not a hard disk. Once a conversation moves past the window, those tokens are gone; the model cannot "remember" them the way you remember yesterday. Every inference call starts fresh with whatever tokens you pack into the window.

The Math: 128K Tokens ≈ 96K Words

A rough rule of thumb is that 1 token ≈ 0.75 English words (or equivalently, 1 word ≈ 1.33 tokens). So a 128,000-token context window holds roughly 96,000 words — about the length of a full novel. That sounds enormous, but in production the space fills up fast: a system prompt might claim 2K tokens, conversation history another 20K, retrieved documents 40K, and the model's own output reserve eats 4K+. Suddenly your "128K window" has only 60K tokens of usable space for the actual task.

Output Eats From the Same Budget

A critical detail many developers miss: the model's generated output counts against the same context window. If you have a 128K window and your input uses 126K tokens, the model can only generate ~2K tokens of output before hitting the wall. This is why you must always reserve output space when planning your budget. The output reservation is not optional — it is a hard constraint that determines the maximum length of the model's response.

"Lost in the Middle" Phenomenon

Research has shown that LLMs pay the most attention to tokens at the beginning and end of the context window, with reduced attention to content in the middle. This is sometimes called the "lost in the middle" effect. In practical terms, if you bury a critical fact at position 60K in a 128K context, the model may overlook it even though it is technically "in context." This means that how you arrange information matters as much as whether it fits.

Longer Context ≠ Better Answers

More context can actually hurt performance. Adding irrelevant documents to fill the window introduces noise that competes with signal during attention computation. Studies show that retrieval-augmented models perform better with 5 highly relevant passages than with 50 loosely related ones. The key insight: context is expensive real estate. Every token you add should earn its place by contributing to the answer.

Context as RAM, Not Disk

  • Volatile: Context is rebuilt from scratch on every API call. There is no persistence between calls unless you explicitly re-send the history.
  • Fixed size: You cannot dynamically expand the window. The model was trained with a specific maximum, and exceeding it causes either truncation or an error.
  • Shared bus: Input and output share the same bus. Heavy input means light output capacity, and vice versa.
  • Latency-coupled: Attention is O(n²) in sequence length. A 128K context is not just 16x the cost of an 8K context — the attention computation alone is 256x more expensive.
  • Quality-coupled: The model's ability to utilize context degrades with length due to attention dispersion, positional encoding limits, and the "lost in the middle" effect.

# ─── Context Window Budget Calculator ───
# Helps you plan how to allocate tokens across the different
# components that compete for space in the context window.

from dataclasses import dataclass, field
from typing import Dict

# Use a dataclass so each budget allocation is self-documenting
@dataclass
class ContextBudget:
    # Total tokens the model supports (e.g., 128000 for GPT-4-Turbo)
    window_size: int = 128000

    # Fixed overhead: system prompt rarely changes between calls
    system_prompt: int = 2000

    # Reserve for the model's response — this is NON-NEGOTIABLE
    # because output tokens eat from the same window
    output_reserve: int = 4096

    # Safety margin to prevent edge-case truncation
    safety_margin: int = 500

    # Conversation history — grows with each turn
    history_tokens: int = 0

    # Retrieved documents from RAG pipeline
    retrieved_tokens: int = 0

    @property
    def fixed_overhead(self) -> int:
        # These are always present — you can't negotiate them away
        return self.system_prompt + self.output_reserve + self.safety_margin

    @property
    def available_for_content(self) -> int:
        # What's left after fixed costs — this is the REAL budget
        return self.window_size - self.fixed_overhead

    @property
    def remaining(self) -> int:
        # Tokens still free after everything is allocated
        used = self.fixed_overhead + self.history_tokens + self.retrieved_tokens
        return self.window_size - used

    def can_fit(self, new_tokens: int) -> bool:
        # Check BEFORE adding content — prevents overflow errors
        return new_tokens <= self.remaining

    def utilization_report(self) -> Dict[str, float]:
        # Returns percentage breakdown — useful for monitoring dashboards
        total = self.window_size
        return {
            "system_prompt": self.system_prompt / total * 100,
            "history": self.history_tokens / total * 100,
            "retrieved": self.retrieved_tokens / total * 100,
            "output_reserve": self.output_reserve / total * 100,
            "safety": self.safety_margin / total * 100,
            "free": max(0, self.remaining) / total * 100,
        }

# ─── Example: Plan a RAG pipeline budget ───
budget = ContextBudget(
    window_size=128000,
    system_prompt=2500,     # Detailed system instructions
    output_reserve=4096,    # Allow long-form answers
    safety_margin=500,      # Buffer for tokenizer variance
)

# Simulate adding conversation history (10 turns, ~800 tokens each)
budget.history_tokens = 8000

# Check how many retrieved chunks we can afford
print(f"Available for retrieval: {budget.remaining:,} tokens")
# Output: Available for retrieval: 112,904 tokens

# Add retrieved documents — always check before adding!
chunks = [1500, 2200, 1800, 3100, 900]  # 5 RAG chunks
for chunk_size in chunks:
    if budget.can_fit(chunk_size):
        budget.retrieved_tokens += chunk_size
    else:
        print(f"Cannot fit chunk of {chunk_size} tokens — budget full")
        break  # Stop adding once we run out of space

# Final report shows where every token went
for category, pct in budget.utilization_report().items():
    print(f"  {category:<20} {pct:5.1f}%")
Follow-up Questions
What exactly is the "lost in the middle" problem, and how do I mitigate it?
The "lost in the middle" phenomenon, documented by Liu et al. (2023), shows that large language models attend most strongly to tokens near the beginning and end of their context window, with significantly reduced attention to content in the middle. In retrieval-augmented setups, this means the most relevant document should be placed either first or last in the retrieved set, not buried in the middle. Practical mitigations include re-ranking retrieved passages so the most important ones bookend the context, keeping total context shorter to reduce the middle zone, and using explicit "focus" instructions that direct the model to specific sections.
How does context length affect latency and cost?
Transformer self-attention scales quadratically with sequence length — O(n²) — meaning doubling your context roughly quadruples the attention computation cost. In practice, API providers charge per token (both input and output), so a 100K-token prompt costs proportionally more than a 10K-token one. But the latency impact is even steeper: beyond the per-token cost, the "time to first token" increases with input length because the model must process all input tokens before generating any output. This makes context length optimization one of the highest-leverage performance improvements you can make.
What is the difference between effective and theoretical context length?
A model might advertise a 128K or even 1M token context window, but its "effective" context — the length at which it can reliably retrieve and reason about information — is often much shorter. Benchmark tests like "Needle in a Haystack" reveal that many models start losing accuracy on retrieval tasks well before their theoretical maximum. Effective context depends on the task: simple fact retrieval may work at 100K tokens, but multi-step reasoning typically degrades beyond 20-30K tokens even in models with much larger windows. Always test your specific use case at the context lengths you plan to use.
How do different models handle long context differently?
Different architectures use different strategies for extending context. Standard transformers use positional encodings (like RoPE) that can be interpolated or extrapolated to longer sequences, though with quality degradation. Some models, such as those using Sparse Attention or Sliding Window Attention (like Mistral), reduce the O(n²) cost by only attending to local neighborhoods plus selected global tokens. Others, like Mamba and RWKV, use recurrent or state-space architectures that process sequences in O(n) time but sacrifice the ability to attend to arbitrary positions. The tradeoff is always between computational cost, maximum length, and quality of attention at long distances.

Why Output Tokens Cost More

Input processing (called "prefill") can be parallelized: all input tokens are known upfront and can be processed in a single batched forward pass. Output generation ("decode") is inherently sequential — each token depends on all previous tokens, so the model must run a separate forward pass for every single output token. This sequential bottleneck means output tokens consume far more GPU time per token, which is why providers charge 2–4x more for them.

How Batching Reduces Cost

Modern inference engines (vLLM, TensorRT-LLM, etc.) batch multiple requests together so they share GPU compute. During the prefill phase, different requests' input tokens can be processed in parallel across the batch dimension. During decode, the engine interleaves generation steps from different requests to keep the GPU busy while any single request waits for its next token. This is why API pricing can be lower than running your own GPU — providers amortize compute across thousands of concurrent users.

Token-Efficient Prompting Strategies

  • Trim system prompts ruthlessly. Every token in your system prompt is repeated on every API call. A 500-token reduction at 10K requests/day saves 5M tokens/day.
  • Use structured output formats. Asking for JSON with a strict schema produces fewer wasted tokens than asking for prose. Constrained decoding also reduces output length.
  • Set max_tokens wisely. If you only need a yes/no answer, set max_tokens to 10, not 4096. This prevents the model from rambling and saves output token costs.
  • Cache repeated prefixes. Many providers offer prompt caching: if the first N tokens of your request match a cached prefix, you skip their prefill cost. Design prompts with a stable prefix (system prompt + few-shot examples) to maximize cache hits.
  • Summarize history instead of appending. Instead of sending the entire conversation history, periodically summarize older turns. This keeps input tokens bounded as conversations grow.

# and the provider's per-token pricing.

from typing import Optional

# Pricing is per 1M tokens — store as millionths for clean math
@dataclass
class ModelPricing:
    # Price per 1M input tokens (prefill phase)
    input_per_million: float

    # Price per 1M output tokens (decode phase — always higher)
    output_per_million: float

    # Optional: cached input discount (e.g., 0.5 = 50% off)
    cached_input_discount: float = 0.0

# Common model pricing as of 2024 (prices change — always verify!)
PRICING = {
    "gpt-4-turbo":   ModelPricing(10.0,  30.0,  0.5),
    "gpt-4o":        ModelPricing(2.5,   10.0,  0.5),
    "gpt-4o-mini":   ModelPricing(0.15,  0.6,   0.5),
    "claude-sonnet": ModelPricing(3.0,   15.0,  0.1),
    "claude-haiku":  ModelPricing(0.25,  1.25,  0.1),
}

def estimate_cost(
    input_tokens: int,
    output_tokens: int,
    model: str,
    cached_input_tokens: int = 0,
    requests_per_day: int = 1,
) -> dict:
    """Calculate cost for a single call and projected daily/monthly spend."""

    pricing = PRICING.get(model)
    if not pricing:
        raise ValueError(f"Unknown model: {model}")

    # Non-cached input tokens charged at full rate
    fresh_input = input_tokens - cached_input_tokens

    # Cached tokens get a discount — saves money on repeated prefixes
    cached_cost = (cached_input_tokens / 1_000_000) * \
        pricing.input_per_million * (1 - pricing.cached_input_discount)

    # Fresh input at full price
    fresh_cost = (fresh_input / 1_000_000) * pricing.input_per_million

    # Output tokens are the expensive part — 2-4x input price
    output_cost = (output_tokens / 1_000_000) * pricing.output_per_million

    # Total per-call cost
    per_call = cached_cost + fresh_cost + output_cost

    return {
        "per_call": round(per_call, 6),
        "daily": round(per_call * requests_per_day, 4),
        "monthly": round(per_call * requests_per_day * 30, 2),
        "input_pct": round((fresh_cost + cached_cost) / per_call * 100, 1),
        "output_pct": round(output_cost / per_call * 100, 1),
        "cache_savings": round(
            (cached_input_tokens / 1_000_000) *
            pricing.input_per_million * pricing.cached_input_discount, 6
        ),
    }

Follow-up Questions
How does prompt caching work and when should I use it?
Prompt caching works by storing the key-value (KV) pairs computed during the prefill phase for a given prefix of tokens. When a subsequent request shares the same prefix, the provider can skip recomputing those KV pairs and charge a reduced rate (typically 50-90% off the input token price). You should use caching whenever your prompts share a stable prefix, such as a system prompt, few-shot examples, or a base set of documents. The cache hit requires an exact token-for-token match of the prefix, so design your prompts with the stable part first and variable content at the end.
What are practical ways to reduce output token costs?
Output tokens typically cost 2-4x more than input tokens, so reducing output length is highly leveraged. Set the max_tokens parameter to the minimum needed for your use case. Use structured output formats (JSON schemas, enums) that constrain the model to concise responses. Ask explicitly for brevity in your system prompt ("respond in under 100 words"). For classification tasks, instruct the model to return only the label, not an explanation. Use stop sequences to halt generation as soon as the answer is complete. Finally, consider using a smaller, cheaper model for tasks that do not require frontier-level reasoning.
How do batching and concurrency affect API costs?
Most LLM providers offer a Batch API that processes requests asynchronously at a 50% discount because the provider can schedule them during off-peak GPU time. This is ideal for non-real-time workloads like document processing, evaluations, or data labeling. Concurrency (sending many requests simultaneously) does not directly reduce per-token cost, but it increases throughput, which reduces total wall-clock time. However, hitting rate limits causes requests to queue or fail, so you need to implement exponential backoff. Some providers also offer throughput-based pricing tiers where committed volume gets a lower per-token rate.
Why do output tokens cost more than input tokens?
The cost difference comes down to how transformers process input versus output. During the "prefill" phase, all input tokens are processed in parallel in a single forward pass through the model. This is very GPU-efficient because it maximizes utilization of the parallel compute units. During the "decode" phase, the model generates output tokens one at a time, each requiring its own forward pass. This sequential process means the GPU sits partially idle waiting for each token to complete before starting the next. The result is that generating 1,000 output tokens requires roughly 1,000 separate forward passes, while processing 1,000 input tokens requires just one. This fundamental asymmetry is why output costs 2-4x more.

The Three Overflow Strategies

1. Truncation

Truncation is the simplest approach: when content exceeds the context window, you cut it at the boundary. Most implementations truncate from the end (keeping the beginning), but some truncate from the beginning (keeping the most recent content, useful for chat history). The advantage is speed and simplicity — no additional API calls, no compute overhead. The danger is severe: you might cut away the exact paragraph that contains the answer. Truncation makes the model confidently answer based on incomplete evidence, which is worse than admitting it does not have enough information.

2. Sliding Window

A sliding window scans across the document in overlapping chunks. Each chunk is processed independently, and results are aggregated. This ensures every part of the document gets "seen" by the model, but at the cost of multiple API calls and the loss of global context — the model never sees the whole document at once, so it cannot reason about relationships between distant sections. The overlap between windows is critical: too little overlap and you miss information that spans a chunk boundary; too much overlap and you waste tokens re-processing content. A typical overlap is 10-20% of the window size.

3. Smart Retrieval (RAG)

Retrieval-based selection uses embeddings or keyword search to identify which chunks of the document are most relevant to the user's query, then includes only those chunks. This is the most token-efficient approach and generally produces the best results for question-answering tasks. However, it depends entirely on the quality of the retrieval step: if the retriever misses a relevant chunk, the model will never see it. It also requires pre-processing (chunking and embedding the document), which adds latency on first use.

Why "Just Use a Bigger Context" Does Not Solve Everything

Larger context windows introduce three problems that people underestimate. First, cost scales linearly with input tokens and the attention mechanism scales quadratically, so doubling context length roughly quadruples compute cost. Second, the "lost in the middle" problem means that adding more content can actually decrease accuracy by burying the relevant information deeper in the context. Third, latency increases significantly — a 200K token prompt takes much longer to process than a 20K token prompt, which matters for user-facing applications.

Noise Is Worse Than Absence

A critical insight for production systems: including irrelevant context is often worse than excluding relevant context. When you pack the context window with loosely related documents, the model must attend to all of them, diluting its attention on the actually relevant content. Studies show that RAG systems with 5 highly relevant passages outperform systems with 20 passages where only 5 are relevant. The extra 15 passages do not just waste tokens — they actively interfere with the model's ability to find and reason about the right information. This is why retrieval quality matters more than retrieval quantity.

# ─── Three Overflow Strategies ───
# Each strategy handles the same problem differently:
# "My input has more tokens than the context window allows."

from typing import List, Tuple

# ── Strategy 1: Truncation ──
# The guillotine approach — fast but potentially destructive.
# Use when you know the important content is at the start (or end).
def truncate(
    tokens: List[str],
    max_tokens: int,
    keep: str = "start"  # "start" keeps beginning, "end" keeps most recent
) -> List[str]:
    """Cut tokens to fit the budget. Simple but lossy."""
    if len(tokens) <= max_tokens:
        return tokens  # Already fits — no truncation needed

    if keep == "start":
        # Keep the first N tokens (good for documents with frontmatter)
        return tokens[:max_tokens]
    else:
        # Keep the last N tokens (good for chat history — most recent is most relevant)
        return tokens[-max_tokens:]


# ── Strategy 2: Sliding Window ──
# Scan the document like a spotlight, processing each chunk independently.
# The overlap prevents missing info that spans chunk boundaries.
def sliding_window(
    tokens: List[str],
    window_size: int,
    overlap: int = 200,  # Tokens shared between adjacent windows
) -> List[List[str]]:
    """Split tokens into overlapping chunks for sequential processing."""

    # Step size = how far we advance between windows
    # Smaller step = more overlap = more cost but fewer missed boundaries
    step = window_size - overlap
    if step <= 0:
        raise ValueError("Overlap must be smaller than window_size")

    chunks = []
    for start in range(0, len(tokens), step):
        end = min(start + window_size, len(tokens))
        chunks.append(tokens[start:end])

        # Stop if we've reached the end — no point creating empty chunks
        if end >= len(tokens):
            break

    return chunks  # Each chunk is processed as a separate API call


# ── Strategy 3: Smart Retrieval (RAG) ──
# Only include chunks that are relevant to the user's query.
# This is the most token-efficient approach for Q&A tasks.
def smart_retrieval(
    chunks: List[List[str]],
    query_embedding: List[float],
    chunk_embeddings: List[List[float]],
    max_tokens: int,
    min_relevance: float = 0.7,  # Only include chunks above this threshold
) -> List[Tuple[int, List[str]]]:
    """Select the most relevant chunks that fit within the token budget."""

    # Score each chunk by cosine similarity to the query
    scores = []
    for i, emb in enumerate(chunk_embeddings):
        # Cosine similarity: dot(a,b) / (|a| * |b|)
        dot = sum(a * b for a, b in zip(query_embedding, emb))
        mag_q = sum(x**2 for x in query_embedding) ** 0.5
        mag_e = sum(x**2 for x in emb) ** 0.5
        similarity = dot / (mag_q * mag_e + 1e-8)  # Epsilon prevents division by zero
        scores.append((i, similarity))

    # Sort by relevance — most relevant chunks first
    scores.sort(key=lambda x: x[1], reverse=True)

    # Greedily pack the most relevant chunks until budget is full
    selected = []
    used_tokens = 0
    for idx, score in scores:
        if score < min_relevance:
            break  # Below threshold — remaining chunks are noise, not signal

        chunk_len = len(chunks[idx])
        if used_tokens + chunk_len > max_tokens:
            continue  # Does not fit — try a smaller chunk

        selected.append((idx, chunks[idx]))
        used_tokens += chunk_len

    # Re-sort by original position to preserve document order
    # This helps the model understand the narrative flow
    selected.sort(key=lambda x: x[0])

    return selected

Follow-up Questions
When should I choose truncation over summarization?
Choose truncation when the relevant information has a known position in the document (e.g., the most recent messages in a chat log, the header section of an email), when latency is critical (truncation is instant, summarization requires an API call), and when the cost of an additional LLM call for summarization outweighs the risk of information loss. Choose summarization when information is distributed throughout the document, when you need to preserve key facts from all sections, and when you can afford the extra latency and cost of the summarization call. A common hybrid approach is to truncate to a rough window, then summarize the truncated portion to compress it further.
What is hierarchical summarization and when is it useful?
Hierarchical summarization is a multi-level compression strategy where you first split a long document into chunks, summarize each chunk independently, then summarize the summaries. This can be repeated multiple levels deep for very long documents. It is useful when the document is far too long for even a single summarization call (e.g., a 500-page book), and when you need a coherent high-level understanding rather than specific details. The main risk is "summary drift" — each level of summarization introduces distortion, so details get progressively less accurate. For fact-critical applications, combine hierarchical summarization with retrieval: use the summaries to identify which sections are relevant, then retrieve the original text of those sections.
How does map-reduce work for processing long documents with LLMs?
Map-reduce for LLMs borrows the concept from distributed computing. In the "map" phase, you split the document into chunks and process each chunk independently with the same prompt (e.g., "extract all key claims from this section"). In the "reduce" phase, you combine all the map outputs into a single prompt and ask the model to synthesize them (e.g., "given these extracted claims from all sections, produce a unified summary"). This approach scales to arbitrarily long documents because each map call fits within the context window. The tradeoff is cost (you pay for N+1 API calls instead of 1) and the loss of cross-chunk reasoning during the map phase. LangChain and LlamaIndex both provide built-in map-reduce chains for common tasks like summarization, extraction, and question-answering over long documents.

Truncation: The Guillotine

Truncation is seductive because it is free and instant. But it creates a dangerous illusion: the model receives a partial document and treats it as the complete document. If a user asks "what are the conclusions?" and the conclusions section was truncated away, the model will either hallucinate conclusions based on the introduction, or say it cannot find them. The former is far more common and far more dangerous. Truncation works well only when you have strong prior knowledge about where the important content lives — for example, keeping the most recent N messages in a chat, or keeping the first page of a document that always starts with an executive summary.

Sliding Windows: The Spotlight

Sliding windows ensure full coverage at the cost of multiple API calls and the loss of global context. The critical design decision is the overlap size. Too small an overlap (say, 50 tokens) risks splitting a key paragraph across two windows with neither window containing enough context to understand it. Too large an overlap (say, 50% of the window) doubles your API costs with diminishing returns. A good rule of thumb is 10-20% of the window size, or enough tokens to contain at least 2-3 complete paragraphs. For structured documents with clear section boundaries, you can reduce overlap by aligning window boundaries with section breaks.

Summarization: The Lossy Compressor

Summarization trades exact content for compressed meaning. A 10,000-token section can be compressed to 500 tokens while preserving the key ideas. The quality depends heavily on the summarization prompt and the model doing the summarizing. Common failure modes include: losing specific numbers and dates, merging distinct claims into ambiguous generalizations, and introducing subtle inaccuracies when the model "fills in" gaps in its understanding. Summarization works best when combined with retrieval: summarize for context, but retrieve the original text when the model needs to cite specific evidence.

The Production Hybrid Pattern

In production systems, these strategies are rarely used in isolation. A common hybrid approach works like this: (1) Use retrieval to identify the most relevant chunks for the current query. (2) For chunks that fit in the window, include them verbatim. (3) For remaining context (conversation history, background documents), use summarization to compress them. (4) If the compressed result still exceeds the window, truncate the least relevant summaries. This layered approach maximizes information density while respecting the token budget. The key principle is: preserve fidelity for the content most likely to contain the answer, and compress everything else.

# for handling documents that exceed the context window.

from typing import List, Dict, Any
import math

# ── Strategy 1: Truncation ──
# Ruthlessly simple: cut at the boundary, keep what fits.
def truncate_chunks(
    chunks: List[Dict[str, Any]],
    max_tokens: int,
    direction: str = "keep_start"
) -> Dict[str, Any]:
    """Keep chunks from the start (or end) until budget is full."""

    # Reverse the list if we want to keep the end (most recent content)
    ordered = chunks if direction == "keep_start" else chunks[::-1]

    kept, dropped = [], []
    used = 0
    for chunk in ordered:
        if used + chunk["tokens"] <= max_tokens:
            kept.append(chunk)
            used += chunk["tokens"]
        else:
            dropped.append(chunk)  # Everything past the limit is lost

    # Restore original order if we reversed
    if direction != "keep_start":
        kept = kept[::-1]

    return {
        "kept": kept,
        "dropped": dropped,
        "tokens_used": used,
        "info_loss": sum(c["tokens"] for c in dropped),  # Tokens we will never see
    }


# ── Strategy 2: Sliding Window ──
# Scan the document in overlapping windows, process each one.
def sliding_window_process(
    chunks: List[Dict[str, Any]],
    window_tokens: int,
    overlap_ratio: float = 0.15,  # 15% overlap between windows
) -> List[List[Dict[str, Any]]]:
    """Split chunks into overlapping windows for sequential processing."""

    # Calculate overlap in tokens — this is the "safety net" zone
    # where adjacent windows share content to prevent boundary misses
    overlap_tokens = int(window_tokens * overlap_ratio)
    step_tokens = window_tokens - overlap_tokens  # How far to advance per window

    # Build cumulative token positions for each chunk
    positions = []
    running = 0
    for c in chunks:
        positions.append({"start": running, "end": running + c["tokens"], "chunk": c})
        running += c["tokens"]

    total_tokens = running
    windows = []
    win_start = 0

    while win_start < total_tokens:
        win_end = win_start + window_tokens

        # Include any chunk that overlaps with this window's range
        window_chunks = [
            p["chunk"] for p in positions
            if p["end"] > win_start and p["start"] < win_end
        ]
        windows.append(window_chunks)

        # Advance by step_tokens (not window_tokens) to create overlap
        win_start += step_tokens

    return windows  # Each window is one API call


# ── Strategy 3: Summarization ──
# Compress early content into summaries, keep recent content verbatim.
def summarize_and_pack(
    chunks: List[Dict[str, Any]],
    max_tokens: int,
    summarize_fn,  # Callable that compresses text — your LLM summarizer
    compression_ratio: float = 0.2,  # Summaries are ~20% of original size
) -> Dict[str, Any]:
    """Compress older chunks into summaries, keep recent chunks verbatim."""

    # First, check if everything fits without compression
    total = sum(c["tokens"] for c in chunks)
    if total <= max_tokens:
        return {"chunks": chunks, "summaries": [], "calls": 0}

    # Work backward from the end: keep recent chunks verbatim
    # because recent context is usually more relevant
    verbatim = []
    verbatim_tokens = 0
    for chunk in reversed(chunks):
        if verbatim_tokens + chunk["tokens"] <= max_tokens * 0.6:
            verbatim.insert(0, chunk)  # Preserve order
            verbatim_tokens += chunk["tokens"]
        else:
            break  # Remaining older chunks need compression

    # Everything not kept verbatim gets summarized
    to_summarize = chunks[:len(chunks) - len(verbatim)]
    remaining_budget = max_tokens - verbatim_tokens

    summaries = []
    for chunk in to_summarize:
        # Each summary uses ~20% of the original token count
        summary_tokens = int(chunk["tokens"] * compression_ratio)
        if summary_tokens <= remaining_budget:
            # Call the LLM to produce a compressed summary
            summary_text = summarize_fn(chunk["text"])
            summaries.append({
                "text": summary_text,
                "tokens": summary_tokens,
                "original_tokens": chunk["tokens"],
                "source": chunk.get("title", "unknown"),
            })
            remaining_budget -= summary_tokens

    return {
        "summaries": summaries,    # Compressed older content
        "verbatim": verbatim,      # Recent content kept intact
        "calls": len(summaries),    # Number of summarization API calls
        "compression": round(       # How much space we saved
            (1 - sum(s["tokens"] for s in summaries) /
             max(1, sum(s["original_tokens"] for s in summaries))) * 100, 1
        ),
    }

Follow-up Questions
How do you decide the right overlap size for sliding windows?
The overlap should be large enough to contain at least one complete semantic unit (a paragraph, a code block, a table row) so that information spanning a window boundary is fully captured in at least one window. For English prose, 10-20% of the window size typically works well, which translates to roughly 400-800 tokens for a 4K window. For structured data like code or JSON, align window boundaries with structural boundaries (function definitions, object closures) rather than using fixed overlap. You can also measure empirically: run your pipeline with different overlaps and check whether the aggregated results miss any ground-truth facts that span boundaries. Larger overlaps increase cost linearly (more total tokens processed) but reduce boundary-miss risk logarithmically, so there are diminishing returns beyond about 25%.
What is recursive summarization and when does it break down?
Recursive (hierarchical) summarization splits a document into chunks, summarizes each chunk, then summarizes the summaries, repeating until the result fits in the target budget. Each level typically compresses by 3-5x, so two levels of summarization can compress a 100K-token document to ~4K-7K tokens. It breaks down in three situations: (1) when exact details matter — each summarization level introduces "drift" where numbers get rounded, qualifiers get dropped, and nuances get flattened; (2) when the document contains complex cross-references — the chunk-level summarizer cannot see relationships between distant sections; (3) when the document is highly heterogeneous — a legal contract with both boilerplate and critical clauses might get the critical clauses averaged into the boilerplate during summarization. Always validate recursive summaries against the original for factual accuracy in high-stakes applications.
Can summarization be done incrementally as new content arrives?
Yes, incremental (or "streaming") summarization is a common pattern in production chat applications. Instead of re-summarizing the entire conversation history on every turn, you maintain a running summary and update it with each new turn. The prompt looks like: "Given this existing summary and this new conversation turn, produce an updated summary." This keeps the summarization cost constant per turn (O(1)) rather than growing with conversation length (O(n)). The tradeoff is that errors compound: if the running summary misrepresents something early in the conversation, that error propagates through all future updates. A mitigation is to periodically re-summarize from scratch (e.g., every 20 turns) to reset any accumulated drift, or to keep a small window of recent verbatim messages alongside the running summary for grounding.

Budget Rules of Thumb

  • Reserve output first. Decide the maximum response length your application needs, then subtract it from the window before allocating anything else. If you need 4K tokens of output, that is non-negotiable — everything else must fit in the remaining space. Forgetting this reservation is the most common budgeting mistake.
  • System prompts should be under 5% of the window. If your system prompt is 10K tokens on a 128K window, you are spending 8% of your budget on instructions that repeat identically on every call. Audit your system prompt quarterly: remove redundant instructions, compress examples, and move static reference data to retrieval.
  • Keep a 5-10% safety margin. Tokenizer estimates are approximate — different tokenizers produce different counts for the same text. A safety margin prevents edge-case overflows that cause API errors or silent truncation.
  • History should be capped, not unbounded. In multi-turn conversations, keep the most recent N turns verbatim and summarize everything older. Without a cap, a long conversation will eventually consume the entire window, leaving no room for retrieved context or output.
  • Measure real-world distributions, not averages. Your average request might use 40K tokens, but the P99 might use 120K. Budget for the tail, not the mean, or implement graceful degradation for outlier requests.
  • Retrieved context has diminishing returns. The first 3-5 relevant chunks add the most value. Each additional chunk adds less signal and more noise. Measure the marginal impact of additional chunks on answer quality to find the optimal number for your use case.

Common Mistakes

  • Forward budgeting: Starting with content and hoping it fits, rather than starting with the budget and fitting content into it. This leads to frequent overflows and inconsistent behavior.
  • Ignoring output tokens: Treating the context window as if it is only for input. The model's output shares the same window, and a long output reservation shrinks input capacity significantly.
  • Static budgets for dynamic content: Using the same token allocation for every request when the content varies wildly. A question about a short email and a question about a 100-page report should not use the same budget split.
  • No overflow handling: Having no strategy for what happens when content exceeds the budget. Every production system needs a fallback: truncate, summarize, or return an error with a clear message.
  • Over-retrieval: Retrieving 20 chunks "just in case" when 5 would suffice. This wastes tokens, increases cost, and can degrade answer quality due to noise dilution.

Monitoring in Production

Token budgeting is not a one-time design decision — it requires ongoing monitoring. Track these metrics in your production dashboard:

  • Token utilization distribution: What percentage of the window are you typically using? If you are consistently under 30%, you might be paying for a larger model than you need. If you are consistently over 90%, you are at risk of overflow.
  • Overflow rate: How often do requests exceed the window? Even a 1% overflow rate means some users are getting truncated or failed responses. This should be an alerting metric.
  • Output truncation rate: How often does the model hit max_tokens before finishing its response? This indicates your output reservation is too small.
  • Cost per request distribution: Track the P50, P90, and P99 cost per request. A long tail indicates highly variable content that might benefit from adaptive budgeting or tiered processing.
  • Cache hit rate: If you are using prompt caching, track the hit rate. A low hit rate means your prompt prefix is too variable, and you are not getting the cost savings you expect.
Python Example 
# ─── TokenBudget: Production Token Budget Manager ───
# A class that enforces token budgets in production LLM pipelines.
# Design principle: reserve non-negotiables first, then allocate the rest.

from dataclasses import dataclass, field
from typing import Dict, List, Optional, Tuple
import logging

logger = logging.getLogger("token_budget")

@dataclass
class TokenBudget:
    """Manages token allocation across all components of an LLM call.

    Usage: Create a budget, reserve fixed costs, then allocate the
    remaining space to variable content (history, retrieval, etc.).
    """

    # The model's maximum context window — this is the hard ceiling
    window_size: int = 128_000

    # Safety margin — protects against tokenizer estimation errors
    # Different tokenizers (tiktoken, sentencepiece) give different counts
    safety_margin_pct: float = 0.05

    # Fixed reservations — these are non-negotiable and allocated first
    system_prompt_tokens: int = 0
    output_reserve: int = 4096  # MUST be set — output shares the window
    guardrail_tokens: int = 0   # Content filters, safety instructions

    # Tracking allocations as they're made
    _allocations: Dict[str, int] = field(default_factory=dict)

    @property
    def effective_window(self) -> int:
        # The REAL budget after safety margin — always use this, not window_size
        return int(self.window_size * (1 - self.safety_margin_pct))

    @property
    def fixed_costs(self) -> int:
        # Total tokens that are reserved regardless of content
        return self.system_prompt_tokens + self.output_reserve + self.guardrail_tokens

    @property
    def available(self) -> int:
        # What's left for variable content (history + retrieval + query)
        used = self.fixed_costs + sum(self._allocations.values())
        return max(0, self.effective_window - used)

    @property
    def utilization(self) -> float:
        # Percentage of window used — track this in your monitoring dashboard
        total_used = self.fixed_costs + sum(self._allocations.values())
        return total_used / self.effective_window

    def allocate(self, name: str, tokens: int) -> bool:
        """Try to allocate tokens for a component. Returns False if no room."""
        if tokens > self.available:
            logger.warning(
                f"Cannot allocate {tokens} tokens for '{name}' — "
                f"only {self.available} available"
            )
            return False  # Caller must handle the overflow

        self._allocations[name] = tokens
        return True

    def allocate_proportional(
        self, components: Dict[str, int]
    ) -> Dict[str, int]:
        """Allocate remaining space proportionally between competing components.

        Args:
            components: dict mapping name -> desired_tokens
        Returns:
            dict mapping name -> actually_allocated_tokens
        """
        total_desired = sum(components.values())
        budget = self.available

        if total_desired <= budget:
            # Everything fits — allocate exact amounts
            for name, tokens in components.items():
                self._allocations[name] = tokens
            return dict(components)

        # Scale down proportionally so everything fits
        scale = budget / total_desired
        result = {}
        for name, desired in components.items():
            actual = int(desired * scale)
            self._allocations[name] = actual
            result[name] = actual

        return result

    def check_health(self) -> List[str]:
        """Return a list of warnings about the current budget state.

        Run this before every API call to catch problems early.
        """
        warnings = []

        if self.utilization > 0.95:
            warnings.append("CRITICAL: Over 95% utilization — high overflow risk")
        elif self.utilization > 0.85:
            warnings.append("WARNING: Over 85% utilization — consider trimming")

        if self.output_reserve < 1000:
            warnings.append("WARNING: Output reserve under 1K — responses may truncate")

        if self.system_prompt_tokens > self.effective_window * 0.1:
            warnings.append("INFO: System prompt exceeds 10% of window — consider trimming")

        if self.available < 0:
            warnings.append("CRITICAL: Budget exceeded — request will fail or truncate")

        return warnings

    def report(self) -> str:
        """Human-readable budget report for logging and debugging."""
        lines = [f"Token Budget Report (window: {self.window_size:,})"]
        lines.append(f"  Effective (after {self.safety_margin_pct*100:.0f}% margin): {self.effective_window:,}")
        lines.append(f"  System prompt:  {self.system_prompt_tokens:,}")
        lines.append(f"  Output reserve: {self.output_reserve:,}")
        lines.append(f"  Guardrails:     {self.guardrail_tokens:,}")
        for name, tokens in self._allocations.items():
            lines.append(f"  {name:<16} {tokens:,}")
        lines.append(f"  Available:      {self.available:,}")
        lines.append(f"  Utilization:    {self.utilization*100:.1f}%")
        return "\n".join(lines)

Follow-up Questions
How do you budget tokens for multi-turn agent loops?
Agent loops are the hardest budgeting challenge because the number of turns is unpredictable. Each agent turn adds both the model's reasoning/action output and the tool/observation result to the context. A robust approach is to set a "per-turn budget" that includes the maximum tool output size plus the expected reasoning length, then calculate the maximum number of turns as: (available_tokens - system_prompt - output_reserve) / per_turn_budget. When the agent approaches this limit, implement graceful degradation: summarize earlier turns, reduce tool output verbosity, or force the agent to produce a final answer. Some frameworks (like LangChain's ConversationSummaryBufferMemory) automatically summarize older turns when the context exceeds a threshold, keeping the most recent turns verbatim for accuracy.
What metrics should I monitor for token budgets in production?
Track five key metrics: (1) Token utilization distribution (P50, P90, P99) across all requests to understand typical and worst-case usage. (2) Overflow rate, defined as the percentage of requests that exceed the context window and require fallback handling. This should be an alertable metric with a target under 0.1%. (3) Output truncation rate, measuring how often the model hits max_tokens before completing its response, which indicates your output reserve is too small. (4) Cost per request distribution, broken down by input and output tokens, to catch cost spikes from unexpected input growth. (5) Latency by token count, which helps you set appropriate timeouts and identify requests where context reduction would improve user experience. Dashboard these metrics with 24-hour rolling windows and set alerts on the overflow and truncation rates.
How does prompt caching interact with token budgeting?
Prompt caching reduces cost but does not change the token budget. Even though cached tokens are cheaper to process (typically 50-90% discount), they still count against the context window limit. This means caching is a cost optimization, not a capacity optimization. However, caching does influence how you design your budget: you should front-load the stable, cacheable content (system prompt, few-shot examples, static reference data) at the beginning of your prompt, then append variable content (user query, retrieved documents) at the end. This maximizes the cache prefix length. A subtlety: if you reorder content to optimize for retrieval quality (e.g., putting the most relevant document first), you may break your cache prefix, forcing a tradeoff between cache hit rate and retrieval effectiveness.
What is graceful degradation for token budgets?
Graceful degradation is a strategy where, instead of failing when content exceeds the budget, you progressively reduce content quality to maintain functionality. A typical degradation ladder looks like this: (1) Full quality: all retrieved documents, full conversation history, detailed system prompt. (2) First reduction: summarize conversation history older than 5 turns, reduce retrieved documents from 10 to 5. (3) Second reduction: compress all history to a single summary paragraph, reduce to 3 retrieved documents, trim system prompt to essentials. (4) Emergency mode: drop all history, keep only the 1 most relevant document and a minimal system prompt. Each level should be tested to ensure acceptable answer quality. The key is defining these levels in advance and implementing automatic fallback, rather than discovering overflow in production and returning an error. Log which degradation level each request triggers so you can tune your budgets if too many requests hit lower levels.
