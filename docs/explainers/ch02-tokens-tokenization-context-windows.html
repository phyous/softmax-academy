What Is a Token?

Quick Take: A token is the atomic unit an LLM processes — not a word, not a character, but a statistical building block. Every cost, speed, and memory metric in LLMs is measured in tokens.
Tokens will appear here...
Tokens: 0 Characters: 0 Chars/Token: 0

Deep Dive

  • LLMs never see raw text — the tokenizer converts strings to integer IDs from a fixed vocabulary before anything else happens.
  • Vocabulary is learned during training via algorithms like BPE (Byte-Pair Encoding). Modern vocabularies typically contain 32k–100k tokens.
  • Token ≠ word: "tokenization" → ["token", "ization"], "the" → ["the"], "🎉" → multiple tokens. The mapping is statistical, not linguistic.
  • Everything downstream is token-denominated: API pricing (cost per 1k tokens), context limits (max tokens in/out), latency (tokens per second), and output budgets.
  • "128k context" = 128,000 tokens ≈ 96,000 words (not 128k words). The common English ratio is roughly 1 token ≈ 0.75 words, but this varies wildly by content type.
Python Example 
import tiktoken

# Use the cl100k_base encoding (GPT-4, GPT-3.5-turbo)
enc = tiktoken.get_encoding("cl100k_base")

text = "Tokenization is fascinating!"
tokens = enc.encode(text)
pieces = [enc.decode([t]) for t in tokens]

print(f"Text:    {text}")
print(f"Tokens:  {tokens}")
print(f"Pieces:  {pieces}")
print(f"Count:   {len(tokens)} tokens, {len(text)} chars")
print(f"Ratio:   {len(text)/len(tokens):.1f} chars/token")

# Output:
# Text:    Tokenization is fascinating!
# Tokens:  [5765, 2065, 374, 27387, 0]
# Pieces:  ['Token', 'ization', ' is', ' fascinating', '!']

Tokens vs Words

Quick Take: Human language is messy — prefixes, suffixes, code, emoji, and multilingual text break any clean word-to-token mapping. Tokenizers optimize for statistical efficiency, not human readability.

Deep Dive

Input Type Word Count Token Count Ratio Why
Simple English ~10 ~12 1.2x Common words map 1:1
JSON ~8 ~25 3.1x Brackets, quotes, colons each cost a token
Source code ~15 ~40 2.7x Indentation, operators, special chars
CJK text ~1 (no spaces) ~15 15x Each character may fragment into multiple tokens
Emoji ~3 ~12 4x Multi-byte sequences require several tokens

This ratio matters because it determines real cost. A JSON API response that "looks short" can cost 3x more than the natural-language equivalent with the same information. When designing prompts, formats, and RAG pipelines, token efficiency is a first-class concern.

Byte-Pair Encoding (BPE)

Quick Take: BPE builds a vocabulary bottom-up — start with characters, repeatedly merge the most frequent pair. Common patterns get compact tokens; rare words decompose gracefully. No word is truly "unknown."

Corpus
Top Pairs
PairCount
Vocabulary (0)

Deep Dive

  • Before BPE: Fixed word vocabularies assigned [UNK] to any unseen word — a dead end for rare names, typos, and new slang. The model literally could not process unfamiliar text.
  • The algorithm: Start from individual characters → count all adjacent pairs → merge the most frequent pair into a new token → repeat until the target vocabulary size is reached.
  • Result: A spectrum of token granularity:
    • Very common words → single dedicated tokens ("the", "and")
    • Common morphemes → shared tokens ("ing", "tion", "un")
    • Rare strings → decompose into character-level pieces
  • Why it won: Open-vocabulary (no [UNK]), compact representation for common text, and entirely language-agnostic — it works by frequency, not by linguistic rules.
  • Used by: GPT family, LLaMA, most modern LLMs (often with byte-level variants like BBPE that operate on raw bytes instead of Unicode characters).
Python Example 
"""Simplified BPE implementation showing iterative merging."""

def get_pair_counts(corpus):
    """Count frequency of adjacent symbol pairs across all words."""
    pairs = {}
    for word, freq in corpus.items():
        symbols = word.split()
        for i in range(len(symbols) - 1):
            pair = (symbols[i], symbols[i + 1])
            pairs[pair] = pairs.get(pair, 0) + freq
    return pairs

def merge_pair(pair, corpus):
    """Merge all occurrences of a pair in the corpus."""
    merged = {}
    bigram = ' '.join(pair)
    replacement = ''.join(pair)
    for word, freq in corpus.items():
        new_word = word.replace(bigram, replacement)
        merged[new_word] = freq
    return merged

# Corpus: each word split into characters, with frequency
corpus = {
    'l o w':     5,
    'l o w e r': 2,
    'n e w e s t': 6,
    'w i d e s t': 3,
}
vocab = set(ch for word in corpus for ch in word.split())

num_merges = 8
for i in range(num_merges):
    pairs = get_pair_counts(corpus)
    if not pairs:
        break
    best = max(pairs, key=pairs.get)
    corpus = merge_pair(best, corpus)
    vocab.add(''.join(best))
    print(f"Merge {i+1}: {best} -> {''.join(best)} "
          f"(freq: {pairs[best]}, vocab: {len(vocab)})")

# Output:
# Merge 1: ('e', 's') -> es (freq: 9, vocab: 10)
# Merge 2: ('es', 't') -> est (freq: 9, vocab: 11)
# Merge 3: ('l', 'o') -> lo (freq: 7, vocab: 12)
# Merge 4: ('lo', 'w') -> low (freq: 7, vocab: 13)
# Merge 5: ('n', 'e') -> ne (freq: 6, vocab: 14)
# Merge 6: ('ne', 'w') -> new (freq: 6, vocab: 15)
# Merge 7: ('new', 'est') -> newest (freq: 6, vocab: 16)
# Merge 8: ('low', 'e') -> lowe (freq: 2, vocab: 17)

SentencePiece

Quick Take: SentencePiece skips the "split by whitespace first" step — it learns tokenization directly from raw bytes. This makes it the default for multilingual and language-agnostic models.
Input Text
⚙ Classic Pipeline
⚡ SentencePiece Pipeline

Deep Dive

  • Classic tokenizers assume spaces separate words — fine for English and similar scripts, but fundamentally broken for CJK (Chinese, Japanese, Korean), Thai, and many agglutinative languages where word boundaries are not marked by whitespace.
  • SentencePiece treats input as a raw character/byte stream — no pre-tokenization assumptions. It learns segmentation boundaries directly from data, making it truly language-agnostic.
  • Bundles everything into a single portable .model file: vocabulary, normalization rules, and merge rules. No external dependencies or preprocessing scripts needed.
  • Guarantees identical tokenization in training and inference — eliminating subtle preprocessing mismatch bugs that plagued earlier pipelines (e.g., different whitespace normalization between training data prep and serving).
  • Supports both BPE and unigram language model algorithms — the unigram model takes a different approach (starts with a large vocabulary, prunes down) and can produce more linguistically intuitive subwords.
  • Used by: T5, LLaMA, PaLM, mBART, and most multilingual models. If a model supports 100+ languages, it almost certainly uses SentencePiece.
Python Example 
import sentencepiece as spm

# Train a SentencePiece model on raw text
spm.SentencePieceTrainer.train(
    input='corpus.txt',
    model_prefix='my_tokenizer',
    vocab_size=8000,
    model_type='bpe',           # or 'unigram'
    character_coverage=0.9995,  # important for CJK
)

# Load and use the trained model
sp = spm.SentencePieceProcessor(model_file='my_tokenizer.model')

# Encode text — works for ANY language, no preprocessing needed
texts = [
    "The cat sat on the mat",
    "大規模言語モデル",         # Japanese
    "مرحبا بالعالم",           # Arabic
]

for text in texts:
    pieces = sp.encode(text, out_type=str)
    ids = sp.encode(text, out_type=int)
    print(f"Input:  {text}")
    print(f"Pieces: {pieces}")
    print(f"IDs:    {ids}")
    print(f"Decoded: {sp.decode(ids)}")
    print()

# The same .model file handles all languages seamlessly
# No whitespace splitting, no language-specific rules

Special Tokens

Quick Take: Special tokens are invisible structural markers — [BOS], [EOS], [SEP], [PAD] — that tell the model where sequences start, end, and transition. Mishandle them and the model misinterprets everything.
Chat Conversation

Deep Dive

Token Purpose What Breaks Without It
[BOS] Marks sequence start Model does not know where input begins
[EOS] Marks sequence end Model generates forever / cannot stop
[SEP] Separates segments Sentence pairs blur together
[PAD] Fills batches to equal length GPU batching fails or wastes compute
[MASK] Marks prediction target (BERT) MLM training objective breaks
Role markers Separates chat turns User/assistant roles blur
  • Chat models rely on role markers to know "whose turn it is" — remove them and the model cannot distinguish instructions from conversation. This is the structural foundation of prompt injection defenses.
  • Fine-tuning with mismatched special tokens is a top silent bug — the model trains fine (loss decreases) but behaves unpredictably at inference time because the token boundaries are wrong.
  • Different model families use different conventions: OpenAI uses ChatML (<|im_start|>/<|im_end|>), LLaMA uses [INST]/[/INST], and others use custom formats. Mixing them is a common source of bugs.

Context Window

Quick Take: The context window is the model's working desk — everything it can see at once. System prompt, user input, retrieved docs, and the model's own output all compete for the same fixed space.

  • Context window = maximum tokens the model attends to in ONE forward pass. It's a hard ceiling set at training time and enforced at inference.
  • It includes everything: system instructions + user input + retrieved context + chat history + the model's own output.
  • "128k context" = 128,000 tokens ≈ 96,000 words ≈ 300 pages — but that's the theoretical maximum, not the usable budget.
  • The model's own output consumes from the same budget — a 2,000-token response eats 2,000 tokens of context space.
  • Longer context ≠ better answers. Models struggle with "lost in the middle" — information placed in the middle of long contexts receives less attention than content at the start or end.
Key Insight: Context is like RAM, not disk. Only what's loaded can be used. This is why context management is engineering, not an afterthought.
Python Example 
def calculate_context_budget(
    window_size: int = 128_000,
    system_prompt_tokens: int = 500,
    max_output_tokens: int = 4_096,
    guardrail_tokens: int = 200,
) -> dict:
    """Calculate available token budget for dynamic content.

    Always reserve non-negotiable space first, then allocate
    the remainder to conversation history and retrieved context.
    """
    reserved = system_prompt_tokens + max_output_tokens + guardrail_tokens
    available = window_size - reserved

    if available < 0:
        raise ValueError(
            f"Reserved tokens ({reserved:,}) exceed window size ({window_size:,}). "
            f"Reduce system prompt or output limit."
        )

    # Rule of thumb: 60% retrieval, 30% history, 10% buffer
    budget = {
        "window_size": window_size,
        "system_prompt": system_prompt_tokens,
        "max_output": max_output_tokens,
        "guardrails": guardrail_tokens,
        "total_reserved": reserved,
        "available_for_content": available,
        "suggested_retrieval": int(available * 0.60),
        "suggested_history": int(available * 0.30),
        "safety_buffer": int(available * 0.10),
    }

    return budget


# Example usage
budget = calculate_context_budget(window_size=128_000)
print(f"Window:    {budget['window_size']:>8,} tokens")
print(f"Reserved:  {budget['total_reserved']:>8,} tokens")
print(f"Available: {budget['available_for_content']:>8,} tokens")
print(f"  Retrieval: {budget['suggested_retrieval']:>6,}")
print(f"  History:   {budget['suggested_history']:>6,}")
print(f"  Buffer:    {budget['safety_buffer']:>6,}")

# Output:
# Window:    128,000 tokens
# Reserved:     4,796 tokens
# Available: 123,204 tokens
#   Retrieval: 73,922
#   History:   36,961
#   Buffer:    12,320

  • Token efficiency isn't just a billing concern — it directly affects user-perceived latency.
  • Verbose formats (JSON, XML, markdown) are 2–3x more expensive than compact natural language for the same semantic content.

Python Example 
import json

def estimate_cost(
    text: str,
    output_tokens: int = 500,
    input_rate: float = 0.015,   # $ per 1K input tokens
    output_rate: float = 0.060,  # $ per 1K output tokens
) -> dict:
    """Estimate cost for a prompt, comparing token efficiency."""
    # Rough tokenization: ~4 chars per token for English
    input_tokens = len(text) // 4

    input_cost = (input_tokens / 1000) * input_rate
    output_cost = (output_tokens / 1000) * output_rate
    total_cost = input_cost + output_cost

    return {
        "input_tokens": input_tokens,
        "output_tokens": output_tokens,
        "input_cost": round(input_cost, 6),
        "output_cost": round(output_cost, 6),
        "total_cost": round(total_cost, 6),
    }


# Compare: natural language vs JSON for the same request
natural = "Summarize the key findings from the quarterly sales report focusing on growth trends."
structured = json.dumps({
    "task": "summarize",
    "source": "quarterly_sales_report",
    "focus": ["year_over_year_growth", "regional_differences"],
    "format": "bullet_points",
    "max_length": 500
})

cost_nl = estimate_cost(natural)
cost_json = estimate_cost(structured)

print(f"Natural language: {cost_nl['input_tokens']} tokens, ${cost_nl['total_cost']:.4f}")
print(f"JSON structured:  {cost_json['input_tokens']} tokens, ${cost_json['total_cost']:.4f}")
print(f"JSON overhead:    {cost_json['input_tokens'] - cost_nl['input_tokens']} extra tokens")
print(f"Cost increase:    {((cost_json['total_cost'] / cost_nl['total_cost']) - 1) * 100:.1f}%")

# At 1M requests/month:

Input Exceeds Context

Quick Take: When input overflows the context window, something has to give. The system must truncate, compress, or selectively retrieve — and doing it badly means the model answers confidently with missing evidence.
10 / 16
  • Naive truncation (drop from end or start) is cheap but dangerous — can remove the actual question or key evidence.
  • Sliding windows process overlapping segments — preserves local detail but loses global coherence across windows.
  • Summarization compresses early content — preserves the gist but loses exact quotes and numbers.
  • Retrieval-based selection (rank chunks by relevance, pick top-K) almost always beats brute-force context stuffing.
  • Even with 128k+ context, don't blindly fill it — irrelevant context degrades answer quality ("noise is worse than absence").
  • Production systems combine strategies: summarize old history + retrieve relevant chunks + preserve system instructions.
Best Practice: Retrieval-based selection almost always beats brute-force stuffing. Relevant context in a small window outperforms irrelevant context in a large one.
Python Example 
from typing import List

def truncate_chunks(
    chunks: List[str],
    max_chunks: int,
    keep_first: int = 1,
    keep_last: int = 1,
) -> List[str]:
    """Truncate middle chunks, preserving start and end.

    Keeps system instructions (first) and user query (last).
    """
    if len(chunks) <= max_chunks:
        return chunks
    # Always keep first chunk (system prompt) and last (user query)
    first = chunks[:keep_first]
    last = chunks[-keep_last:]
    middle_budget = max_chunks - keep_first - keep_last
    middle = chunks[keep_first:keep_first + middle_budget]
    return first + middle + last


def sliding_window(
    chunks: List[str],
    window_size: int,
    overlap: int = 2,
) -> List[List[str]]:
    """Generate overlapping windows across chunks.

    Each window is processed independently; results are merged.
    """
    windows = []
    step = max(1, window_size - overlap)
    for i in range(0, len(chunks), step):
        window = chunks[i:i + window_size]
        if window:
            windows.append(window)
    return windows


def selective_retrieval(
    chunks: List[str],
    query: str,
    max_chunks: int,
    system_chunks: List[str] = None,
) -> List[str]:
    """Select most relevant chunks via simple keyword overlap.

    In production, use embeddings + vector similarity instead.
    """
    query_words = set(query.lower().split())

    scored = []
    for i, chunk in enumerate(chunks):
        chunk_words = set(chunk.lower().split())
        overlap = len(query_words & chunk_words)
        scored.append((overlap, i, chunk))

    scored.sort(key=lambda x: -x[0])
    selected = [c for _, _, c in scored[:max_chunks]]

    if system_chunks:
        selected = system_chunks + selected

    return selected


# Example
chunks = [f"Document chunk {i}: content about topic {chr(65+i)}" for i in range(16)]
print("Truncated:", len(truncate_chunks(chunks, max_chunks=8)))
print("Windows:", len(sliding_window(chunks, window_size=6, overlap=2)))
print("Retrieved:", len(selective_retrieval(chunks, "topic A", max_chunks=5)))

Truncation vs Sliding Windows vs Summarization

Quick Take: Three overflow strategies, three different tradeoffs. Truncation is a guillotine — fast but ruthless. Sliding windows are a spotlight scanning a dark room. Summarization is a note-taker who captures the gist but loses the quotes.

  • Truncation risk: cutting from the start loses system instructions; from the end loses the question.
  • Sliding windows need overlap (typically 10–20%) to avoid missing information at boundaries.
  • Summarization quality depends on the summarizer — bad summaries are worse than truncation.
Production Pattern: Hybrid approach — summarize old history + retrieve fresh chunks + always preserve system prompt and user query.
Python Example 
from typing import List, Callable

def strategy_truncate(
    chunks: List[str],
    budget: int,
    keep_start: int = 1,
    keep_end: int = 1,
) -> dict:
    """Truncation: keep first and last, cut the rest."""
    n = len(chunks)
    if n <= budget:
        return {"result": chunks, "lost": 0, "passes": 1}

    first = chunks[:keep_start]
    last = chunks[-keep_end:]
    middle_budget = budget - keep_start - keep_end
    middle = chunks[keep_start:keep_start + max(0, middle_budget)]
    result = first + middle + last
    return {"result": result, "lost": n - len(result), "passes": 1}


def strategy_sliding_window(
    chunks: List[str],
    window_size: int,
    overlap: int = 2,
    process_fn: Callable = None,
) -> dict:
    """Sliding window: process overlapping segments."""
    windows = []
    step = max(1, window_size - overlap)
    for i in range(0, len(chunks), step):
        window = chunks[i:i + window_size]
        if window:
            windows.append(window)

    results = []
    for w in windows:
        if process_fn:
            results.append(process_fn(w))
        else:
            results.append(" ".join(w))

    return {
        "windows": len(windows),
        "results": results,
        "overlap_tokens": overlap * len(windows),
        "passes": len(windows),
    }


def strategy_summarize(
    chunks: List[str],
    budget: int,
    summarize_fn: Callable = None,
    preserve_recent: int = 3,
) -> dict:
    """Summarization: compress old chunks, keep recent ones."""
    n = len(chunks)
    if n <= budget:
        return {"result": chunks, "compressed": 0, "passes": 1}

    recent = chunks[-preserve_recent:]
    to_compress = chunks[:-preserve_recent]

    if summarize_fn:
        summary = summarize_fn(to_compress)
    else:
        summary = f"[Summary of {len(to_compress)} chunks]"

    result = [summary] + recent
    return {
        "result": result,
        "compressed": len(to_compress),
        "summary_length": len(summary),
        "passes": 2,  # one pass for summarization, one for final answer
    }


# Compare all three strategies
chunks = [f"Chunk {i}: important data about topic {chr(65 + i % 26)}" for i in range(20)]
budget = 8

trunc = strategy_truncate(chunks, budget)
slide = strategy_sliding_window(chunks, window_size=budget, overlap=2)
summ = strategy_summarize(chunks, budget)

print(f"Truncation: {len(trunc['result'])} chunks, lost {trunc['lost']}, {trunc['passes']} pass")
print(f"Sliding:    {slide['windows']} windows, {slide['passes']} passes")
print(f"Summary:    {len(summ['result'])} chunks, compressed {summ['compressed']}, {summ['passes']} passes")

Token Budgeting in Production

Quick Take: Design prompts backward from the budget, not forward from the content. Reserve space for non-negotiables first (system prompt, output, guardrails), then let everything else compete for what remains.

Budget Rules of Thumb:
  • Reserve output budget FIRST — the model's response competes with input for the same window.
  • System prompt + guardrails are non-negotiable — never let them get squeezed out.
  • Retrieved context should be ranked by relevance — don't stuff all chunks, pick top-K.
  • Conversation history grows every turn — implement summarization or sliding window for older messages.

Common Mistakes

  • Not reserving output space → model response gets truncated mid-sentence.
  • Stuffing all retrieved chunks → irrelevant context dilutes answer quality.
  • Ignoring history growth → works in testing, overflows in production after 10+ turns.
  • Using average token counts → p99 overflow causes intermittent failures that are hard to debug.

Monitoring

  • Track token usage distributions (avg, p50, p95, p99) — averages hide overflow spikes.
  • Alert on overflow events — treat them like errors, not warnings.
  • Treat token budget as a reliability metric alongside latency and error rate.
Python Example 
from dataclasses import dataclass, field
from typing import Optional
import warnings


@dataclass
class TokenBudget:
    """Manages token allocation across context window components.

    Design philosophy: reserve non-negotiables first,
    then distribute remaining capacity by priority.
    """
    window_size: int = 128_000
    system_prompt: int = 500
    guardrails: int = 300
    output_reserve: int = 4_096
    user_query: int = 500

    # Dynamic allocations (filled at runtime)
    retrieved_context: int = 0
    conversation_history: int = 0

    def _fixed_cost(self) -> int:
        return (self.system_prompt + self.guardrails +
                self.output_reserve + self.user_query)

    @property
    def available_for_dynamic(self) -> int:
        """Tokens available for retrieval + history."""
        return max(0, self.window_size - self._fixed_cost())

    @property
    def total_used(self) -> int:
        return (self._fixed_cost() +
                self.retrieved_context +
                self.conversation_history)

    @property
    def remaining(self) -> int:
        return self.window_size - self.total_used

    @property
    def utilization(self) -> float:
        return self.total_used / self.window_size

    @property
    def is_overflow(self) -> bool:
        return self.total_used > self.window_size

    def allocate(
        self,
        history_tokens: int,
        retrieval_tokens: int,
    ) -> "TokenBudget":
        """Allocate dynamic content, with overflow protection."""
        budget = self.available_for_dynamic

        if history_tokens + retrieval_tokens <= budget:
            self.conversation_history = history_tokens
            self.retrieved_context = retrieval_tokens
        else:
            # Priority: retrieval > history (history can be summarized)
            self.retrieved_context = min(retrieval_tokens, budget)
            remaining = budget - self.retrieved_context
            self.conversation_history = min(history_tokens, remaining)

            if history_tokens + retrieval_tokens > budget:
                warnings.warn(
                    f"Content ({history_tokens + retrieval_tokens:,} tokens) "
                    f"exceeds budget ({budget:,}). "
                    f"History truncated to {self.conversation_history:,}."
                )
        return self

    def report(self) -> str:
        lines = [
            f"Window:       {self.window_size:>8,}",
            f"System:       {self.system_prompt:>8,}",
            f"Guardrails:   {self.guardrails:>8,}",
            f"Query:        {self.user_query:>8,}",
            f"Retrieval:    {self.retrieved_context:>8,}",
            f"History:      {self.conversation_history:>8,}",
            f"Output:       {self.output_reserve:>8,}",
            f"{'─' * 28}",
            f"Used:         {self.total_used:>8,}",
            f"Remaining:    {self.remaining:>8,}",
            f"Utilization:  {self.utilization:>7.1%}",
        ]
        if self.is_overflow:
            lines.append(f"⚠ OVERFLOW by {-self.remaining:,} tokens!")
        return "\n".join(lines)


# Example: RAG pipeline budget
budget = TokenBudget(window_size=128_000, output_reserve=4_096)
budget.allocate(history_tokens=8_000, retrieval_tokens=40_000)
print(budget.report())
